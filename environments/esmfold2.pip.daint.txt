# ESMFold2 on Daint (aarch64 / NGC PyTorch image).
#
# Identical to esmfold2.pip.txt except numpy is pinned below 2 and esm is pinned to a commit, with torch left out entirely.
#
# The image's torch is compiled against NumPy 1.x. Installing pandas pulls NumPy 2.x into the venv, where it shadows the image's numpy and every torch.from_numpy call fails at fold time with:
#
#     RuntimeError: Numpy is not available
#
# The traceback points at esm/models/esmfold2/prepare_input.py, which makes it look like an esm bug; it is an ABI mismatch. Pinning numpy<2 resolves it.
#
# Listing torch here cannot work: the builder constrains it to the image's local version (torch==2.8.0a0+...nv25.6), which exists on no index, so any torch requirement resolves to ResolutionImpossible. The image supplies it.
#
# esm is pinned against the unpinned-installs rule because the image forces it: from v3.4.0 (2026-08-27) upstream requires torch>=2.11.0,<2.12.0, which the image cannot provide. 26b0bc2 (2026-07-28, version 3.3.0) is the last commit that still accepts torch>=2.2.0 and carries ESMFold2.
# NOT INSTALLABLE as of 2026-10-11, and no version of this file is: every 3.3.0-era commit needs `transformers @ git+https://github.com/Biohub/transformers.git`, which now 404s, and the versions that dropped that fork need the torch this image cannot provide. Fix by moving the EDF to an NGC image with torch 2.11 and unpinning esm.
# config.daint.yaml therefore does not list ESMFold2 (neither under environments: nor under edf:), and this file is the record of why. The wrapper itself needs esm >= 3.4, which a 3.3.0 pin cannot satisfy.
