# Changelog

All notable changes to biopipelines and its tool wrappers are recorded here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/) for the framework version (`biopipelines.__version__` in `biopipelines/__init__.py`).

Each release section has two subsections:

- **Framework** — changes to `biopipelines/`-internal infrastructure (`Pipeline`, `BaseConfig`, debug capture, CLI, shared `pipe_scripts/` helpers). Tracked by the framework version.
- **Tools** — wrapper changes that bumped a tool's `TOOL_VERSION`. Each bullet names the tool, the old → new version, and a one-line note. Mirrors the `current` field in `tool_changelog.yaml`.

The pre-commit hook (`versions/check_tool_edits.py`) refuses any commit that modifies a wrapper or its mapped pipe scripts without bumping the tool's `current` in `versions/tool_changelog.yaml` AND adding a matching bullet under `[unreleased] → Tools` here.

## [unreleased]

### Upgrading from 1.4.1

The public repository goes from 1.4.1 to this release directly, so these are the 1.5.0 changes a 1.4.1 pipeline can notice:

- **ProteinMPNN / LigandMPNN on a multi-chain backbone** now emit one `sequences` row per chain instead of one row with the chains joined by `/` or `:`. With the default `chains=None` a multi-chain design is recorded in `missing.csv` naming its chains; pass `chains=["A", "B"]` (ids `<design>_<chain>`) or `chains="all"`, and fold the rows back together with `Grouped(mpnn)`. Single-chain pipelines are unchanged.
- **`chain=` on both MPNNs** binds `chains=`, which also restricts the rows to that chain; a chainless position selection on a multi-chain structure now raises.
- **RFdiffusion3** takes `/0` as the chain break; `\0` is refused.
- **`config.cluster.yaml`** keeps AlphaFold and its parameters under `<group>/models/localcolabfold`; a checkout still using `<data>/localcolabfold` needs `AlphaFold.install()` again, or its overlay pointed back.
- **Templates** are `my_pipelines/_template.py`, `my_pipelines/_template.ipynb` and `my_scripts/_template.py`.
- **`llm/cluster.md`, `llm/daint.md` and `llm/log.sh` are gone**; the backend references are in `skills/biopipelines/references/`, and runs are driven through `bp-mcp` or plain ssh.

### Framework

- **Per-ID ancestry.** `biopipelines/ancestry.py` builds the parent graph of a campaign: which design came from which input, across every step. `bp_lineage` counts IDs and `bp_ancestry` connects them, so "prove this design came from that structure" is now answerable from the run itself. Each link carries the basis it was established on -- `recorded` where a step wrote the parent id into a `<axis>.id` column, `matched` where it was resolved with the same id ladder the framework uses at runtime to wire one step into the next. Parent search is scoped by the wiring in `RunTime/pipeline_graph.json`, and an ID whose parent neither tier resolves is reported as a root rather than given an invented link. Ancestry is a DAG: a predicted complex has both its designed chain and its tag as parents, and reporting only one hides half a binder campaign. Rules and the four table shapes it has to read are in `docs/design/id-ancestry.md`.
- `Ssh.id_columns()` / `LocalFS.id_columns()` project the `id` and `<axis>.id` columns of every map table under a run in one round trip, so a large campaign costs one ssh call rather than one per step. The remote reader is stdlib-only and imports no `biopipelines`, so ancestry reads a cluster whose checkout is older than the caller's.
- The provenance page gains an Ancestry panel, and `bp_ancestry(csv=True)` writes `ancestry.csv`, one row per link.
- **A pipeline that passed a table had no manifest.** `TableInfo` answers every public attribute with a column reference, so the manifest's `TOOL_NAME` probe matched it and `os.path.basename` then raised on the reference; `write()` swallowed that and the run was left with no provenance record. `Panda(tables=...)` and every `(tool.tables.x, "col")` selection hit it. Markers are now read off the type, tables and column references render as `<table name step/table/file.csv>`, a value that cannot be rendered degrades to its type instead of taking the manifest with it, and the save-time warning names the error.
- **The hash now covers what it claimed to.** Panda operations (and any dataclass value) are rendered field by field instead of as `<Operation>`, so two runs differing only in a filter threshold no longer share a hash; `Grouped` renders its source and partition; a passed path that names an existing file records the file's sha256 under `input_files`. `compare()` also reports `forwarded`, `input_files`, `class` and unbound `passed` differences, and never returns "no difference" for two different hashes. `environments_were_compared` requires a digest for every environment a step declares, not merely a non-empty map.
- **`Grouped` is walked like `Bundle`/`Each`.** The dataflow-edge walker and the missing-manifest collector both descended only `.sources`, so a `Grouped` input recorded no upstream edge in lineage and ancestry, and its upstream filter's drops were counted as failures.
- The run header records the full commit sha and a `dirty` flag; `--short` picks its length per repository. `bp_reproduce` treats a short recorded sha as matching its full form, points the rerun at the preserved `RunTime/` copy rather than a same-named repo file, no longer sends the source host's `repo` to a different target, and no longer claims to probe environments.

- `resolve_input_to_datastream` resolves a `Grouped` to its source, and a `Grouped` inside a bare list is unwrapped like `Bundle`/`Each` instead of failing with "Cannot extract source paths".

- **`bp-mcp` no longer passes agent-supplied text to a shell unchecked.** `bp_submit(extra=)` went into `./submit {extra}` unquoted and is replaced by `verbose`, the only option `./submit` has; `bp_setup` no longer accepts `prelude` (raw shell run before every command, now set in `.bp-mcp.json` by hand) and validates `python`, `repo` and `variant`; `host` must be an alias, never an ssh option (`-oProxyCommand=` ran on the laptop under ssh < 9.6); remote paths handed to scp are restricted, since a legacy scp expands them in the remote shell, and an upload can no longer target outside the repo. Every ssh/scp call passes `BatchMode=yes`, `ConnectTimeout` and `--`.
- **The documented Daint setup works.** `quote()` single-quoted `$SCRATCH/biopipelines`, so `bp_setup` reported the repository missing and `bp_visualize` could not find its script; a leading `$VAR` now stays expandable, and scp paths resolve it on the remote first.
- **A failure is no longer reported as an answer.** ssh's own exit 255 (auth, network, an expired certificate) raised nothing and read as "no project folder" or "no batch script"; it is now a `RemoteError`. A submit that times out says the outcome is unknown instead of "could not submit", which invited a second submission. `bp_project history`, `bp_setup` and the submit record count report a write that did not happen. stdin goes to ssh as bytes, so files written from Windows no longer get CRLF.
- **`bp_cancel` previews.** Without `confirm=True` it names the jobs the scheduler still holds and cancels nothing; with it, it cancels only those, so ids from earlier submits no longer make a successful cancel read as a failure. A bare job name found in two projects is refused with both listed, in one ssh round trip instead of one per project.
- `bp_lineage(page=True)` and `bp_ancestry(csv=True)` write into the repository's `outputs/_views/` rather than the server's working directory, with the file name sanitized; fetched views are keyed by host and path so two runs no longer overwrite each other; `bp_fetch` refuses to overwrite an existing local file without `overwrite=True`. The remote id-column reader has the same reach as the local one and skips a malformed table instead of failing the whole run.
- **Environment redaction covers the common credential forms.** It missed `KEY: value` YAML (a conda `variables:` block holding `HF_TOKEN`, `WANDB_API_KEY` or AWS keys), uppercase `PASSWORD=`, `hf_`/`sk-`/`pypi-` tokens, anaconda.org `/t/<token>/` channels, and the tail of a password containing an unencoded `@`. Keys now match in any case and only when they end in the secret's name, so `tokenizers==0.15` is left alone. The unredacted capture goes to a private `mktemp` file (`umask 077`) instead of a group-readable `.raw` beside the run.
- **Lineage counts each dropped ID once, where it was dropped.** Every step merges its upstream `missing.csv` into its own, so summing row counts charged one filter's drops again to every later step, inflated the total, and named the last step as the largest loss. A row an earlier step already listed is now counted as inherited, and the provenance page lists a step's own drops only. The remote id-column reader takes the `removed_by` column alongside the ids, in the same round trip.
- `ALIAS_CHANGES` lets a tool say what a retired parameter spelling no longer means, so its `deprecated_alias` line does not claim the pipeline runs unchanged.
- **A run's identity is the run's, not the laptop's.** `bp_submit` wrote the laptop's version, commit and interpreter as the run header, and `bp_status` showed them as what produced the run; they are now filed under `submitted_from`, and `bp_status` takes version, commit and variant from `manifest.json`. `manifest.read` returns `None` only when there is no manifest and raises on anything else, so a corrupt file or a failed read is no longer reported as "that run predates the manifest".
- **Ancestry follows a pass-through id step by step.** Nodes were keyed by id alone, so an id carried unchanged through MPNN, Boltz2 and a filter was traced from the first step holding it and its chain came back flattened into siblings; nodes are now (step, id), a trace starts from the latest producer, and `bp_ancestry(step=)` picks another. A source step after the first (a `Sequence`, a `Ligand`) is a root rather than an unresolved id, and a step's count is its largest stream, not a union inflated by a predictor's echoed `msas`/`compounds` ids.
- Follow-ups from reviewing these fixes: `bp_status` reads only `manifest.json` for the run identity rather than every environment digest (one ssh round trip each); the provenance page filters a step's own drops before truncating; `quote()` expands `${VAR:?}` so an unset variable fails instead of becoming a path under `/`; a hand-written multi-word interpreter in `.bp-mcp.json` is kept as typed; `bp_cancel` recognises array (`123_4`) and het (`123+0`) ids and reports an unreachable controller instead of "nothing to cancel"; `bp_resubmit` reports an ssh failure as an unknown outcome; `bp_setup` and `bp_runs` return a message on an unreachable host; a step missing from the recorded wiring is no longer taken for a source; manifest dataclasses are keyed by `__class__` with a depth cap, input-file hashing stops at 200 files or 1 GB per tool (size only past that), and `compare()` ignores a short sha and a missing `dirty` flag from a 1.5.0 manifest; redaction leaves conda pin lines such as `tiktoken=0.5.1=pypi_0` alone; the rerun hint no longer suggests an absolute `script=` with `upload=`.
### Tools

- **`BFactor` 1.1 -> 1.2** - the chain check counts only chains with residues inside the span; 1.1 counted ligand and water chains too, which failed every unqualified selection on a predicted complex.

- **`ESMFold2` 2.3 -> 2.4** - axis tables are read with string ids, so `001` is not read as `1` and dropped by the id filter 2.3 added.

- **`OpenFold3` 1.2 -> 1.3** - with `top_only=False` the declared ids count every seed (`seeds=[100,101]` at 3 samples writes `_1.._6`, and 3 were declared), and a sample count hidden in `runner_yaml` is refused rather than guessed. The postprocess walks `queries.json` rather than the folders on disk, so a query that failed before inference is recorded as missing instead of vanishing. A csv `msas` stream is refused at configuration; an iterating axis with no records builds no query instead of raising; `install()` no longer recreates an existing env on every call, and still ensures the weights. The docs no longer say the weights download on first prediction, and the AlphaFold3 paper is labelled as the method OpenFold3 reimplements. `pipe_axis_data.py` and `nucleic_acids.py` are now in the `files:` of the tools that import them (Boltz2, OpenFold3, ESMFold2).

- **`BoltzGen` 2.3 -> 2.4** - `install()` applies the local 0.3.1 patches rather than only recording them, on every path including the already-installed shortcut, and fails if they apply to neither state; `boltzgen` is pinned to 0.3.1, the version they target. `smiles_overrides` keys must be CCD-style (1-5 uppercase letters or digits; a lowercase code never matched), and each SMILES is shell-quoted in its export, where a quote or `$` broke or injected into the job script. **BoltzGenImport** 2.2 -> 2.3, **BoltzGenMerge** 2.2 -> 2.3 -- no behavioural change; they share `biopipelines/boltzgen.py`.

- **`BFactor` 1.0 -> 1.1** - an unqualified span on a multi-chain structure is a per-id failure naming the chains, not an average over every chain; a part that is not a span is refused (a typo was an empty selection reported as `n=0`), at configuration time for a literal; insertion-code residues stay separate, with an `icode` column.

- **`DSSP` 2.1 -> 2.2** - a REMARK-3 retry that also fails reports its own error beside the first, and its temporary copy is removed rather than leaking a directory per structure.

- **`PDB` 1.5 -> 1.6** - an RCSB refusal (400/403) is reported at once instead of being retried three times and then described as a network failure; 429 and 5xx are still retried.

- **`Ligand` 1.4 -> 1.5** and **`LASErMPNN` 2.1 -> 2.2** - version bookkeeping only: both pipe scripts changed behaviour in 1.5.0 without a bump, so the old version string named two behaviours. Ligand keeps the ETKDG geometry when MMFF puckers a planar ring system; LASErMPNN size-checks its copies, records empty design files as missing and fails on an empty output table. A 1.5.0 manifest recording Ligand 1.4 or LASErMPNN 2.1 already ran the new code.

- **`ProteinMPNN` 2.6 -> 2.7** and **`LigandMPNN` 2.7 -> 2.8** - the `chain=` deprecation line says the meaning changed instead of "this pipeline still runs as written": `chains=` also decides which chains become `sequences` rows, so `chain="B"` now emits chain B alone. Equal-length chains are assigned by sequence identity to the input chains; both candidate orders matched by length and alphabetical always won, so a design written B-before-A had its sequences swapped. A tie sequence cannot break is reported.

- **`AlphaFold` 1.6 -> 1.7** - pre-computed `msas=` are refused for a `Grouped` complex, as they already were for a `Bundle`: ColabFold folds a complex with its own MSA pipeline and never reads a per-chain a3m, so they were dropped with only a warning. A bare `Grouped(...)` input is accepted too; the input resolver did not know the wrapper, so the constructor raised.

- **`ESMFold2` 2.2 -> 2.3** - a `Grouped` axis folds one complex per group. The wrapper declared one output per group, but the inference script ignored `group_by` and folded every chain row alone, so the declared outputs never appeared. It now uses the shared `group_records`, and also honours the axis `ids` filter a narrowed stream carries.

- **`RFdiffusion3` 3.5 -> 3.6** - the element repair no longer corrupts a spec-compliant PDB. It assumed PDBIO writes segID/element/charge one column early, true through Biopython 1.86; 1.87 writes the spec layout, so the repair read blanks and made every alpha carbon calcium and every SI sulfur. The layout is now read off the installed PDBIO, and a blank element follows the atom-name convention. A `/0` chain break or `\0` inside `json_config` is also seen now, so a multi-chain design given that way declares per-chain `sequences` ids instead of bare ones a consumer would match nothing against.

- **`Boltz2` 2.8 -> 2.9** - the axis reader and the nucleic-acid helpers move into shared modules (`pipe_scripts/pipe_axis_data.py`, `biopipelines/nucleic_acids.py`) so Boltz2 and OpenFold3 read an axis's rows and expand a double-stranded sequence through one implementation. No behaviour change.

- **`OpenFold3` 1.1 -> 1.2** - two bugs found by running it, not by reading about it. The aggregated confidence JSON spells its keys `avg_plddt`, `disorder` and `sample_ranking_score`, so `plddt`, `fraction_disordered` and `ranking_score` came back empty in the first cluster run; the mapping is now taken from a real output and the table gains `gpde`. And `top_only` kept the lowest-numbered sample rather than the best one — upstream writes every sample and ranks them — so it now maximizes `sample_ranking_score`, with `seed` and `sample` recorded so the result says which one it chose.

- **`OpenFold3` 1.0 -> 1.1** - the install downloads the model parameters. Upstream documents them as fetched on first prediction; they are not, and `run_openfold` refuses up front, so a pipeline that installed cleanly died at its first query. Found on the cluster, not locally. `setup_openfold --non-interactive` now runs as part of the install and before the already-installed short-circuit, so an env created by 1.0 acquires its weights on the next install.

- **`OpenFold3` 1.0** (new) - open-source co-folding of proteins, nucleic acids and ligands: the OpenFold Consortium / AlQuraishi lab reimplementation of AlphaFold3, Apache 2.0 with weights included and no access request. Takes the same six input axes as `Boltz2`, so a prediction can be cross-checked against a second model without rewriting the pipeline, and expresses ligands through the same `auth_ligand_field` decision so both receive identical chemistry for the same input. It is not a drop-in replacement: there is no affinity head and ligands are non-covalent, so a binding-affinity readout or a covalent probe stays `Boltz2`. `inference_ckpt_path` runs a privately fine-tuned checkpoint through the same pipeline. The whole batch folds in one process, since `run_openfold predict` takes a single JSON holding every query.

- **`Boltz2` 2.7 -> 2.8** - memory controls, so a complex too large for the GPU can be folded at all. `max_msa_seqs`, `subsample_msa`/`num_subsampled_msa`, `max_parallel_samples` and `no_kernels`, plus `sampling_steps` and `step_scale`. The wrapper refuses `num_subsampled_msa` without `subsample_msa`, because boltz ignores the count without the flag and the run would proceed at full MSA depth and die on the OOM it was configured to avoid.

## [1.5.0] — 2026-09-22

### Framework

**A multi-chain design is several sequence rows, and a step that exits non-zero is never COMPLETED**

- `Grouped(tool.streams.sequences)` -- a bare stream, which is the spelling that reads most naturally -- used to raise, because the group stream was only looked for on a `StandardizedOutput`. A `DataStream` carries `_producer`, the tool that made it, so the sibling `designs` stream is reachable from the stream alone; `get_output_files()` is declarative, so asking the producer for it again at configuration time costs nothing. `Grouped(tool)`, `Grouped(stream)` and an explicit `groups=` now all work, and a stream with no producer still raises naming `groups=`.

- Found in a real campaign, not by testing: four 100-design binder-design runs produced high-confidence complexes of the wrong molecule, and the only tool that noticed was `Prodigy`, which rejected all 393 designs with `Unsupported non-standard amino acid found: UNK`. On a two-chain backbone ProteinMPNN emits both chains in one `sequence` value joined by `/`, `Boltz2` wrote that verbatim into one YAML chain entry, and Boltz mapped the `/` to a `UNK` residue and folded a complex carrying a spurious duplicate of the fixed chain. Nothing warned at any point, and `iptm` came back at 0.94-0.97 for the malformed complex.
- **The framework already had a multi-chain vocabulary and the producer was not using it.** A complex is a `Bundle` of one-row-per-chain — that is how AlphaFold colon-joins its chains and how Boltz2 allocates chain ids. A separator inside one `sequence` cell contradicted that, and nothing in `biopipelines/` or `pipe_scripts/` ever split on one. The fix is at the producer: `pipe_fa_to_csv_fasta.py`, shared by **both** MPNN wrappers, now emits one row per designed chain. See the two tool entries below for the `chains` contract.
- **`Grouped` is the axis that puts them back together.** `Each` makes one output per row and `Bundle` makes one output from every row; neither can say "these rows belong in one prediction". `Grouped(tool)` iterates the *groups* of a stream, taking its partition from a stream of parents exactly as `Consensus` does, and defaulting to the producer's own `designs` stream so nothing has to be wired up. Group ids are known at configuration time even when the member ids are not, so a grouped consumer keeps deterministic output ids whatever `chains=` does. Membership is the framework's id matching, which is why ids as unrelated as `chihuahua+labradudor_1_A` still find their design.
- **A step that exited non-zero could be marked COMPLETED.** `pipe_check_completion.py` judged tables by existence alone and wrote the marker *before* the footer tested `BP_MAIN_RC`; `pipeline.py`'s failure guard then found a COMPLETED marker and declined to write FAILED. So `Prodigy` exiting 1 after producing a header-only `affinity.csv` left the run green — which is what made the corruption above easy to miss. The exit status is now passed to the check and decides first.

**A filter that keeps nothing is no longer reported as a failed step**

- Found by reading a real campaign's runs rather than by testing: five of nine binder-design validation runs showed FAILED steps, and none of them had actually failed. `007_Panda` filtered on `plddt > 80 and RMSD < 2.0`, the four designs came back at 8.6-11.8 A, all four were correctly dropped and recorded — and the step was marked FAILED. Two independent causes, both of which turn "the filter did its job" into "the run broke", which is the one thing a lineage layer must never do.
- **A manifest behind `Bundle`/`Each` was invisible.** `_missing_path_of` requires a source with `.tables`, and the combinatorics wrappers expose only `.sources`. So `Boltz2(proteins=Bundle(filtered_designs, tag))` declared no `missing` table at all, and the 16 outputs its upstream had legitimately filtered away were counted as failures. Any campaign that bundles a filtered stream with a tag lost its drops — the standard sensor-design pattern. The collector now walks into the wrappers, depth first so the documented ordering holds.
- **A shared artifact could never be excused.** Excusal matches a path by its owner id, and one multi-record FASTA for a whole step has none, so with zero survivors nothing wrote it and nothing could excuse it. A stream whose every declared id is excused is now skipped entirely, artifacts included. Deliberately not "give shared files an owner": this rule is smaller and states the real invariant.
- The negative cases are pinned as hard as the positive ones — a partial filter still owes its survivors' files, and a step with no drops recorded that wrote nothing still fails. Otherwise "the filter emptied it" becomes indistinguishable from "the tool is broken".

**`bp_visualize` could not find `bp-visualize`, and `bp_setup` was checking the wrong interpreter**

- `ssh host "<command>"` is a non-interactive, non-login shell: it reads neither `~/.bashrc`'s interactive half nor `/etc/profile.d`, so on S3IT it gets `/usr/bin` and nothing else — no conda, no mamba, and none of the environment's console scripts. `bp_visualize` invoked `bp-visualize` by bare name and could never have worked on that cluster. A host's `python` is now expected to be its *environment's* interpreter, and console scripts are resolved as siblings of it: an env's binaries run by absolute path with no activation, which is simpler and more portable than reconstructing activation across five env managers. An optional per-host `prelude` covers a site where that is not true.
- The same non-interactive shell made `bp_setup`'s import stage meaningless. It ran `cd <repo> && python -c "import biopipelines"`, and `cd <repo>` puts the checkout on `sys.path` — so it passed under `/usr/bin/python` importing the source tree, proving the clone exists and nothing about any environment. It now runs from the home directory and reports which interpreter answered, and a new stage checks that the console scripts behind `bp_visualize` are actually reachable.
- Verified on S3IT: all six stages green with the env interpreter, and `bp_visualize` rendered a real step's page — the first time that tool has run outside a test.

**An ssh alias is named after the site, not after what kind of machine it is**

- The documentation taught `Host cluster`, which reads fine until there is a second cluster — and Daint is also a cluster, so the name stops saying which machine you are on. The setup instructions now show `s3it` and `daint` together and state the rule: the alias is a **place**, the config variant is a **shape**, and they are different namespaces that should not be expected to match. S3IT and any other SLURM/conda site share `variant: cluster`; Daint has its own variant because aarch64, the Container Engine and per-project billing differ, not because it is a particular machine. Every example across the skill, the references and `llm/pipelines.md` was renamed.
- `bp_setup(host=..., forget=True)` drops a saved host, for a renamed alias or a typo — without it, entries accumulate once settings hold several, and a stale one names a machine that may no longer answer. If the forgotten host was the default, the default moves to what remains rather than dangling.

**Two clusters at once: the MCP settings are per host**

- `.bp-mcp.json` held one host, one repo and one interpreter, and `defaults()` returned that repo for *whichever* host a call named. A lab with both S3IT and Daint is the ordinary case, so `bp_status(job=..., host="daint")` was sent S3IT's `~/biopipelines-locbp` — a path that resolves to nothing on Daint, where the checkout has to live on `$SCRATCH`, or worse resolves to something else's tree. The file is now keyed by host and nothing is inherited between them; a flat file from the previous shape is read as a single host, so nobody re-runs setup.
- Two more things could not live in a single slot. **`python`**: Daint's login nodes have no `python` at all, it is a venv on `$SCRATCH`. **`variant`**: the output-root resolver, `./submit`, `./resubmit` and `bp-visualize` all call the framework on the far side, which otherwise takes whatever the remote auto-detects — generating a Daint run against the `cluster` variant produces scripts for a scheduler layout that is not there. A host that pins a variant now exports `BIOPIPELINES_CONFIG_VARIANT` on every remote command; a host that does not is unchanged.
- `bp_setup()` with no arguments lists the configured clusters and marks which one unnamed calls use; `make_default=False` adds one without changing that. All thirteen tools build their connection through one helper, so none can reach a cluster with another's settings — five of them previously constructed their own `Ssh` and would have dropped the interpreter and variant.

**The three operations that still needed a shell now have tools**

- `bp_resubmit` resumes a run that failed partway: it lists the run's batch scripts, refuses to guess when there are several (resubmitting the wrong batch spends compute on work that already succeeded), and strips dependency directives by default because they name the original run's job ids, which have long since finished. `bp_cancel` reads the scheduler ids out of the run's own operations log, so nobody has to find them first, and refuses to send a bare `scancel` when it has none. Both record what they did beside the run.
- `bp_visualize` renders one step and returns the step's images **inline**, with the interactive page fetched to the local machine. The split is the point: plots and rendered images are files and a chat can show them; the page's structure views are 3Dmol.js running in a browser and cannot be shown in a conversation, so the tool says which is which rather than leaving an agent to assume a picture failed to load. It runs on the login node and needs no scheduler, so a finished step can be shown while the rest of the campaign is still queued.
- The server's instructions previously told an agent to shell out for `scancel`, `resubmit` and `bp-visualize`. That list is now `sinfo`/`squeue`.

**W2: the backend references live in the skill, not in `llm/`**

- There were two Daint documents — `llm/daint.md` (operational: certificates, storage, the verified tool list) and `skills/.../references/daint_backend.md` (the variant's venv/EDF mechanism). Two places to keep current about one cluster is the duplication W2 exists to remove. They are now one file, by concatenation rather than rewriting, so nothing was lost. `llm/cluster.md` and `llm/colab.md` moved to `references/cluster_backend.md` and `references/colab_backend.md`.
- These describe a cluster, not a prompt, so the skill is the right home: any host can read a skill reference, while a file under `llm/` is reachable only by a session that was told to read `llm/`. `llm/` now holds the two session prompts and the resources template. Historical references to the old paths in this changelog are left as written.

**`check-updates` asks the repository the checkout actually came from**

- It compared every checkout against GitHub's `main`. For a clone of the internal GitLab that is the wrong line: GitHub's `main` mirrors the `public` branch, so it trails what a lab member tracks, its HEAD is an ancestor of theirs, and the check stayed silent while the line they follow had moved on. It now reads `origin` and asks that, falling back to GitHub only when there is no origin (an export, a tarball). The notice names whichever remote answered.
- Two consequences of asking a private remote, both handled: a URL carrying credentials is stripped to host and path before being printed, so a token in a remote never reaches a job's log; and `GIT_TERMINAL_PROMPT=0` with ssh `BatchMode=yes` make a remote that wants a password fail rather than hang a submit waiting for one — `timeout` bounds that only where GNU coreutils exists. The "what is new" subject list is parsed from GitHub's Atom feed and is simply omitted for other hosts.

**`bp_project` could not reach the cluster at all, and said so as though the project were empty**

- It was the one run-adjacent tool without a `host`, so `project_docs` read a cluster project folder through local `pathlib` and reported `documents: NO, jobs: none` — a perfect description of an empty project, for a folder holding two runs on another machine. `project_docs` now takes `fs=` like `lineage`, `job_status` and `run_log`, working through `is_file`/`read_text`/`append_text`/`listdir`, which both filesystems already implement; `bp_project` takes `host`/`repo` and accepts a project *name* as well as a path, matching what `bp_runs` prints. `survey()` reports `exists` separately, so "not there" and "there but empty" stop being the same answer.

**Reader tests are now anchored to a run the framework built**

- New `produced_run` fixture in `tests/conftest.py`: a real `Pipeline` + `Mock` run whose every path comes from what the tool declared (`stream.map_table`, `tables_folder`, `_compute_log_file_path`), so a fixture cannot hold its own opinion about the layout. The four reader test files were the only ones in the suite that consume an output tree instead of producing one, and three of them had invented one — which is exactly how `bp_table` shipped unable to list a table. `test_lineage`, `test_job_status` and `test_mcp_server` each now carry a case built this way.

**`bp_table` could not see a single table a real step wrote**

- `lineage.tables()` listed `<step>/*.csv`, but the framework puts standalone tables in `<step>/tables/` and a stream's map table in the stream's own folder. Every `bp_table` call on a real run therefore answered "wrote no CSV tables" — a confident denial about a step whose outputs the completion check had just counted. It now searches the step recursively, skipping the framework's own `_`-prefixed folders, and `read_table` accepts `metrics`, `metrics.csv` or `tables/metrics.csv` for the same file. Found by running the pipeline template on S3IT; the unit fixtures had encoded the flat layout, which is why CI was green.
- `resolve_job_dir` returned any path containing a separator unchanged, so `Template/example_002` — the form `bp_runs` prints — became a relative path that resolved to nothing, and `bp_status` reported "No run directory" for a run `bp_runs` had just listed. A non-absolute path is now joined under the output root.

**`bp-mcp`: an MCP server that operates BioPipelines instead of reading about it**

- New optional entry point (`pip install -e ".[mcp]"`, then `claude mcp add --scope user biopipelines -- bp-mcp`). It serves ten tools: `bp_tools` (catalog, one tool's section, or a search by tag/output/input), `bp_setup`, `bp_runs`, `bp_status`, `bp_logs`, `bp_lineage`, `bp_table`, `bp_submit`, `bp_fetch` and `bp_project`. The MCP SDK is an extra, so authoring and running pipelines is unaffected by it.
- The server runs on the user's machine and reaches the cluster over their own ssh alias (`biopipelines/remote.py`, with matching `LocalFS` and `Ssh` back ends), so it needs no install rights on the cluster and leaves no process on a shared login node. It asks the cluster where *its* output root is rather than resolving the local config, because the config resolves `<username>` on the machine that owns it.
- `biopipelines/run_log.py` writes `<Job>_NNN/_operations.jsonl` beside the run: what was submitted, from where, and by which agent. This replaces `llm/log.sh`, which kept an operational log outside the run it described and went stale the moment anyone worked without it.
- `biopipelines/job_status.py` reads completion markers as the source of truth and matches step directories to them by prefix, so a `Suffix`ed step is no longer reported twice — the suffix lands on the folder and the log but not on the marker.
- `biopipelines/project_docs.py` and `bp_project` keep a project folder's two documents: PROJECT.md (goal, inputs, validated protocol) and HISTORY.md (append-only, dated). It never overwrites an existing file; PROJECT.md carries judgment, so an agent drafts and proposes and the scientist owns the content.
- Found and fixed by running the whole chain against S3IT rather than a mock: the remote no longer has to match the laptop's version, cluster logs decode as UTF-8 instead of crashing on cp1252, `host=""` forces local as documented, and the operations log is written on the machine that owns the run.

**Tools can be found by intent, by output, and by capability**

- Every tool section in `docs/tool/*.md` now carries a `**Tags**:` line drawn from a closed 38-term vocabulary in four facets (action, subject, readout, capability), documented in `docs/tool_tags.md`. The vocabulary exists because a capability lives in a parameter, never in the one-line summary: searching the catalog for `covalent` returned nothing, although four tools support it. Terms in one facet are OR-ed and different facets AND-ed, and an exclusion filter is part of the design rather than a refinement — `protein` is carried by three quarters of the catalog and is useful mainly as the thing you filter *against*.
- Tags describe the **wrapper**, not the upstream project. Every capability tag was checked against the upstream repository, which produced a list of capabilities upstream has and BioPipelines does not expose (Gnina's covalent docking and flexible sidechains, ProteinMPNN/LigandMPNN symmetry, ESMFold2 binder inversion, Aggrescan3D's dynamic mode, ProLIF on nucleic acids). Those are feature requests, not tags: a tag promising something unreachable turns an honest miss into a confident wrong answer.
- `biopipelines/tool_schemas.py` answers the question tags answer worst — "which tool gives me an RMSD" — from the tools' own `get_output_files()` via the existing AST extractor: 445 column names, 67 table names and 22 stream names, matched as a case-insensitive substring so `rmsd` reaches `ligand_rmsd`. Nothing there is hand-maintained.
- Six binding-affinity tools gained a `**Units.**` note, surfaced beside every search hit. Boltz2 reports log10(IC50), where lower is stronger; GEMS reports a pKd, where higher is stronger. Nothing had recorded that they run in opposite directions, and a column name alone invites exactly the comparison that is wrong.
- `tests/test_tool_tags.py` keeps it honest: a tag outside the vocabulary fails, a tool with no action tag fails, and a section whose body argues for a capability its tag line omits fails — the one defect no spell-check can see. Four keyword false positives are exempted by name with the reason, and a stale exemption fails too.
- Three README badge links were wrong and are corrected: CABSflex's repo 404'd, BoltzGen pointed at Boltz2's repository and paper, and RFdiffusion2 carried BoltzGen's preprint. All 47 upstream URLs were checked.

**A run records what produced it, without being asked**

- `Pipeline(debug=True)` already captured the environment, and captured it well — full exports, `pip freeze`, `nvidia-smi`, a copy of the active config. But it was opt-in, and the moment that record is wanted is the moment after a result surprised you, by which time the run is over and the flag was off. `save()` now always writes `<job>/manifest.json`: versions, commit, site variant, scheduler, and per step the wrapper version, environments, container image and the parameters both as passed and as resolved. `hash` covers what would make a rerun differ and excludes the timestamp, host and job name, so the same pipeline twice hashes the same.
- The `passed`/`resolved` split is the point. Nobody writes `model_name=`, so a record of typed kwargs cannot say which ProteinMPNN weights produced a set of sequences. `resolved` walks the constructor signatures and reads what each wrapper bound; `passed` is the call itself, captured in `__new__` before a subclass binds its named parameters — `BaseConfig.params` holds only the leftovers, and reading it reported every run as though the user had chosen nothing.
- **The environment is recorded by the run, not by the laptop.** The manifest is written before the job leaves your machine, so it cannot know what will execute it. Each run now exports every environment it uses *with build strings* on the executing node and digests the result into `<job>/environments/<env>.sha256`. `--no-builds` is right for a portable environment file and wrong for identity: two builds of the same versions export identically, which is exactly the distinction that matters now that the same predictor ships in more than one build.
- A consequence that had to be handled explicitly: the manifest hash is sealed at `save()`, so two runs with the same plan and different environments hash the same. `compare()` checks the digests before it short-circuits on the hash, and a run that recorded none is reported as unknown rather than matching — silence would claim the environments agree, which an absent record cannot support.
- **`bp_reproduce`** plans a rerun rather than reconstructing one: a parameter that was a DataStream is recorded as a name, so the wiring is not recoverable from the manifest. It uses what survives — `save()` copies the calling `.py` into `RunTime/` — then asks the target host what it would bring and names every difference before anything is submitted. It submits nothing, and a target that could not be probed is reported as not probed, never as matching. **`bp_provenance`** reads the same record, and with `against=` diffs two runs parameter by parameter.
- **`bp_lineage(page=True)`** renders it for someone who will not call these tools: one self-contained HTML page with the recorded identity, the attrition step by step, the parameters as they resolved, and every dropped ID with the reason its own step gave. Reads through the same filesystem abstraction as the other tools, so a cluster run renders locally without being fetched.
- `Pipeline(debug=True)` raised `NameError` at `save()` on **every** conda or mamba site: `_generate_debug_capture_block` called `cls._env_run(...)`, and neither name exists. It sits in the branch every cluster variant takes, so the forensic capture has never once run there.

**Environment exports are redacted before they are written**

- Found by running the first real campaign rather than by testing, because it needs a scheduled job, an editable install and a clone whose remote URL carries credentials. `pip freeze` renders an editable install as the URL it was cloned from, so the new environment capture wrote a GitLab personal access token in plaintext into an output root that is group-readable on a shared cluster.
- Every export now passes through a redaction filter — URL credentials, GitLab and GitHub token prefixes, and `password=`/`token=`/`secret=`/`api_key=` — before it is kept. The unredacted capture goes to a scratch file that is removed, and only the redacted file is ever digested. If redaction cannot run the export is withheld and no digest is written: an export that might carry a credential is worth less than not having one. The same filter guards the debug capture, which runs its own `pip freeze`.
- This is a backstop, not a permission. Credentials in a clone URL remain readable in `.git/config` to anyone who can read the checkout; use an SSH key or a credential helper, and restrict that file.

## [1.4.1] — 2026-09-16

A patch release on top of `1.4.0`, correcting three faults found after the release commit: two that let a genuinely failed step be stamped `_COMPLETED`, and one that let a CI job silently suppress its own assertions. No API change, and no tool version bumps.

### Framework

**A step's own failure survives the blocks that run after it**

- A generated tool script is a sequence -- the tool's command, optionally the missing-manifest propagation, then the completion check -- with no `set -e`. The script's status is therefore the LAST command's, and both trailing blocks succeed on their own, so a tool that failed exited 0 and `_step_failure_guard` read `${PIPESTATUS[0]}` as clean and wrote no marker. Found on Daint: a `Scripting` step whose `execution()` raised was stamped COMPLETED, with the traceback sitting in its own log. The real status is now captured immediately after the tool's command and re-asserted as the script's exit status, while the trailing blocks still run -- a partly-successful tool still owes downstream a `missing` manifest.

**A value-based stream's map_table is a required output**

- A value-based stream (`files == []`) keeps every row in its map_table, so it declared no per-id path and every existence check was vacuous for it: the tool could write nothing and still pass. In the case above the only output verified was the `missing` table that the trailing block had just created, reported as "1 of 1 declared outputs found". The completion check now requires the map_table of a stream that declares no files. A file-based stream is unchanged -- it is judged by its files, and its map is not required to pre-exist. Audited against four real runs across two clusters and ten tools: 18 of 18 value-based map_tables were already present, so no working step becomes red.

**`check-updates` never derives its sentinel from an empty `GIT_DIR`**

- The once-per-day throttle is keyed on a file under the repo's git dir, resolved with `git rev-parse --absolute-git-dir`. Nothing checked that the answer was non-empty, so a git that returns nothing there made the sentinel path `/.bp-check-updates-day` -- which a root shell really can create at the filesystem root. CI is exactly that shell: `tests/test_check_updates.py` stubs git on PATH and its stub did not answer `rev-parse`, so the first case to run created the sentinel at `/`, every later case in the same job saw today's date and exited silently, and `test_a_behind_checkout_is_reported` asserted on output the throttle had already suppressed. On Windows and on the cluster the write to `/` fails and is swallowed by `|| true`, so the fault surfaced only in CI and only by test order. `check-updates` now exits 0 when `GIT_DIR` is empty instead of writing to `/`, and the test stub answers `rev-parse` with a directory inside each case's own `tmp_path` so the cases cannot throttle one another whatever the user or platform.

## [1.4.0] — 2026-09-11

A minor release on top of `1.3.0`: opt-in container/environment execution switching for external tools, a JSON-config refactor of the resolver-script argument passing, a `grain` parameter for `Panda.merge`, four new tools, and the new contract-enforcement layer.

### Compatibility

Four changes in this release are breaking. Each is listed with what stops working, why it is not deprecated instead, and what to do.

**1. A map_table's file column is always `file`.**

A stream's per-id file path is recorded under `file` in every map_table. `PDB` and `RCSB` wrote `structures` as `file_path`; `AlphaFold`, `Boltz2`, `MMseqs2`, `MSA` and `Mutagenesis` wrote `msas` as `msa_file`. `datastream.create_map_table` — the framework's own writer — always wrote `file`, and `Load` always read only `file`, so these were per-tool drift rather than a convention.

The consequence was silent. Nothing reads that column in a running pipeline: the completion check expands each stream's declared `files` template and stats the paths, and downstream consumers resolve through `iterate_files`, which zips the declared ids and files. It is read in three places only — `Load`, which reconciled the ids and then returned **zero** file paths while reporting "recovered N of N via map_table"; `Pool`, which carried a `("file_path", "file")` probe naming PDB in its comment; and `pipe_gnina`, for Ligand's compounds. So `Load("<run>/003_PDB")` never worked, and `Pool` worked only because of that probe.

There is no alias, because a column name is data on disk and a reader that accepts two names cannot tell a schema from a typo. What changes for you:

- A map_table written by 1.4.0 carries `file`. Any script of your own that reads `file_path` or `msa_file` out of one must read `file`.
- A run folder written **before** 1.4.0 carries the old name. `Load` now refuses it, naming the column and the file, rather than handing back a stream with no files. Rename the column in that CSV to `file`, or re-run the step.
- Auxiliary path columns are unaffected. `Gnina.docking_summary.best_pose_file`, PyMOL's session path and `Ligand.compounds.file_path` name *a* file rather than *the* stream file — `compounds` is value-based and carries no per-id artifact at all — and keep their names.

**2. A bare word inside a `[...]` bracket is a literal, and adjacent classes compile differently.**

`<#>` and `<?>` are the only two match classes. Everything else in a slot is a literal value set, so `[<hits>]` matches the text `hits` and `[_<N>]` matches `_N` — neither is a wildcard, and `[_<chain>]` matched nothing a real run produced. If a pattern of yours reads like a placeholder, it is now a literal; write `<?>` for one segment or `<#>` for a number.

Adjacent classes are rewritten rather than refused, and the rewrite matches exactly the same strings — verified exhaustively over every string of length ≤ 6 for all two- and three-class bodies. `[<#><?>]` compiled to `(?:\d+[^_]+)*`, whose two quantifiers competed for the same characters, so rejecting an id cost one attempt per ordered partition of its run: 395 ms at 22 characters, doubling with each one. It now compiles to `(?:\d[^_]+)?`. `[<?><?>]` gains a correction as well: it used to collapse to `[^_]*`, dropping the two-character minimum that `[<#><#>]` correctly kept.

**3. The retired `<N>` and `<S>` id_map spellings do nothing.**

`id_map_utils`'s classes are `<#>` and `<?>`. `{"*": "*_<S>"}` does not walk up a parent chain — it leaves the id untouched, and silently, with no deprecation notice on that path. Rewrite any stored id_map.

**4. `BIOPIPELINES_ENFORCE` is removed.**

The per-check variables are unchanged: `BIOPIPELINES_ENFORCE_<CHECK>=off|warn|raise` still promotes or silences one check, and is now the only way to make one fatal. Checks still ship at `warn`.

The global switch could not do what it promised. `=off` did not silence everything — the rows reporting a working construction rather than a fault were skipped in both directions. `=raise`, the setting this changelog named for CI, refused every pipeline using `FORWARD_UNKNOWN_KWARGS`, a supported feature; the exemption set added to patch that is what broke the other direction. Replace `=raise` with the per-check variables for the checks you actually want fatal, and `=off` with per-check `=off`.

### Framework

**`bp-visualize` — one step's outputs as a page, while the run is still going**

- Reporting a result meant either prose or `pipeline.html`, and the page is whole-run only: it is written by `save()` and refreshed by `regenerate_pipeline_page`, it renders every step, and it has no way to say "the best five by pLDDT". So a finished step in a queued job had no artifact, and the honest answer was a paragraph describing files the user could not see.
- `bp-visualize <tool folder>` writes `<tool folder>/_extras/<step>_view.html`. It reads the step's exported `ToolOutputs/<step>.json` — which already carries every stream, every table, the output folder and the tool's `rendering_parameters` — plus whatever is on disk, so it needs neither the scheduler nor the pipeline script and does not care whether the rest of the job has finished. It runs on a login node. Registered as `bp-visualize` / `biopipelines-visualize`.
- The renderers are the existing ones: `_rebuild_output`, `_resolve_renderers_config` and `_render_stream_bodies` are reused unchanged, so a step renders here exactly as it does in the run page, vendored py3Dmol inlined and no network. Nothing in it knows what a tool is.
- `--descending <table>.<column>` / `--ascending`, `--max-items N`, `--ids`, `--streams`, `--tables`. The sort key must be **qualified**: a tool's tables can carry one column name twice, so a bare name is refused with the qualified spellings named rather than resolved by guessing.
- The selection reaches the tables too, via a reserved `rendering_parameters["_selection"]`. Without it the page answered one question two ways — a top-5-by-pLDDT view embedded five structures beside a table of every row in file order.
- `--max-items` defaults to **10**, against the run page's own sampling budget of 5. A single-step page carries one step's structures rather than every node's, and 5 hides exactly one item of a 6-item stream. `0` means no cap. The library function keeps 0 as its default, so the opinion lives in the command rather than in `write_view`.
- `--max-items` applies only to the streams the ordering actually ranks. Measured on a real Boltz2 step ordered by `confidence.confidence_score`: it cut the 6 `sequences` and 6 `msas` to 5 beside the intended 30 structures to 5, and the confidence table keys structures — so those items were dropped on no criterion. The page now names each stream it spared and why; with no ordering the cap is a page-size limit and still applies to all. It also overrides the structure viewer's own sampling rather than composing with it. `structures.py` embeds five of a large stream by default (three head, two seeded); returning a *sample* of a requested top-20 answers a different question than the one asked, so an explicit budget takes the head and keeps the caller's order. Without a budget the sampling is untouched.
- Selection projects a stream's map_table onto the chosen ids instead of dropping it. Both `structures._iter_id_file` and `streams.render` prefer the map over the id/file zip, so narrowing `ids` alone would still have rendered every row — and a value-based stream, whose content lives only in the map, would have rendered nothing at all.
- The view lands in `_extras/` because the completion check is declaration-driven: it reads the declared paths and never enumerates a directory (its only `glob` expands declared lazy-id and wildcard patterns), and no tool declares a wildcard inside `_extras/`. `tests/test_visualize.py` pins the verdict as unchanged across writing the page, since "put it beside the outputs" is a good default only while that holds.
- `tests/fixtures/config.local.yaml` declares no renderers, which is what let an earlier viewer regression pass unseen — every bp-visualize test therefore runs under a new `config.renderers_local.yaml` and asserts against the ids the viewer actually embedded, not against the page's text.
- `llm/pipelines.md` now requires it: when a step has produced anything renderable, render it and open it rather than answering in prose, and say so explicitly when that is not possible.

**`resubmit` no longer inherits the original run's dependency directives**

- `submit` resolves the `<JOBID_BATCH_NNN>` placeholders with `sed -i`, so `RunTime/slurm_batch<N>.sh` on disk permanently names the job ids of the run that generated it. `resubmit` handed that file straight back to the scheduler, which is wrong in every case it is used for: a parent that failed or was cancelled leaves the job pending on `DependencyNeverSatisfied` forever (or killed outright under `kill_invalid_depend`), and a parent whose id has aged past `MinJobAge` is either rejected at submission or treated as satisfied depending on site config. The one outcome that worked -- a parent still completed and still remembered -- was the accident.
- Every dependency directive is now stripped by default, for all three schedulers: SLURM's `--dependency` / `-d`, LSF's `-w`, and PBS's `-W depend=` (PBS's other `-W` attributes, e.g. `group_list=`, are left alone). The removed lines are echoed, so a resubmitted job never quietly loses a dependency the user wanted. `--keep-dependencies` retains them for the one case that needs it, a parent batch still queued or running.
- The script is fed to the scheduler through stdin rather than edited in place, so the on-disk record of what the original run submitted stays intact. `sbatch`, `bsub` and `qsub` all accept a job script on stdin.

**One vocabulary for a slot, and a bracket that rejects in linear time**

- `<N>` meant three different things at once. Outside a bracket it was the letter N, which is the notation's whole point. Inside a bracket it silently became a segment wildcard, because `_translate_slot_class` returned `SEGMENT_REGEX` for any content it did not recognise as a class -- so `parent_[<N>]` matched every row, neither the letter nor a number. And in `id_map_utils` it was still a digit class. A slot is a literal value set everywhere now: `prot_[<N>]` covers `prot_`, `prot_N`, `prot_NN`, and nothing else. Write `<#>` for a number and `<?>` for one segment; those two are the only classes.
- `<#>` inside a single-slot bracket compiled to `(?:\d+)*`, the textbook catastrophic-backtracking form: rejecting `hit_` plus 24 digits took **2.03 s**, doubling per digit. `d7efaef` had made exactly this shape linear for the segment class, `31c6187` then respelled six shipped sites from `<N>` to `<#>` on the stated grounds that the compiled regex was identical -- true when written -- and `cd4356c` gave the new spelling a body the collapse did not recognise. Six tools emit it: `panda.py` (three sites), `pool.py`, `remap.py`, and `combinatorics.py` via `aizynthfinder.py`. The collapse now covers the digit class too, and the same 26-digit reject takes **0.0001 s**.
- Nothing in the suite covered the canonical spelling; searching the tests for that bracket returned nothing. `tests/test_id_notation.py` now pins the compiled shape *and* the rejection time, because the timing test alone would pass on a fast machine if the nested quantifier came back.
- `id_map_utils` drops the letter spellings rather than deprecating them, since a slot that is a literal everywhere cannot also be a class anywhere. **A stored id_map of `*_<N>` now raises** instead of being escaped into the literal text `<N>`, which no real id contains -- it would have stripped nothing and reported nothing. `check_retired_class_spelling` is deleted; it had been wired into `parse_id_map_pattern`, which has no production callers, so the deprecation channel it provided never fired.

**A failing step in a Folder, in a pack, or under a scheduler kill**

- The FAILED-marker count was a flat glob of the output root, but `_completion_marker_paths` writes the marker beside the *step* folder -- one level down for a step inside `Folder(...)`, and under `.internal/` for an internal step. The count was structurally zero for both classes, so a grouped step that wrote FAILED and exited 0 still reported COMPLETED and let afterok release every dependent batch. Each batch script now names its own steps' marker paths, so no glob depth can miss one.
- That same count ran over the whole run, and sibling batches under `Parallel()` share one afterok parent and so run at the same time: one batch's failure made its healthy siblings exit non-zero and cancel *their* successors. Naming the paths scopes the count by construction.
- A packed batch called `exit 1` from inside its own body, but the page refresh and the exit check are appended *after* that body -- so a failed packed run skipped both and left the reader the pre-run plan page, the defect `86e253f` and `f51e5d0` fixed for unpacked runs. The pack folds its failures into `BP_FAILED_STEPS` instead; the appended check still produces the non-zero exit.
- A SLURM TIMEOUT or a `scancel` kills the job mid-step, so the `PIPESTATUS` guard never runs and the step writes nothing -- and no marker reads as "not run yet", which is exactly the dead-step-looks-queued case the marker work exists to close. Each script now traps `TERM` and `XCPU`, marks FAILED any step holding neither marker, refreshes the page and exits non-zero. An OOM kill is `SIGKILL` and cannot be trapped; that case is still visible only in `sacct`.
- The trap is tested by running it under a real signal in real bash rather than by grepping the generated text -- a trap that is present and never fires records nothing, and disabling one line fails those tests.

**The global enforce switch stops refusing supported features**

- The manual documents `BIOPIPELINES_ENFORCE=raise` as how a check is made fatal in CI, and it applied to every row -- including the two the code itself labels non-faults, `forwarded_kwargs` ("Informational, not a fault") and `id_match_consistency` ("Log-only"). Measured: the documented setting failed **29 tests** across three suites, and refused every pipeline using `FORWARD_UNKNOWN_KWARGS`, a supported feature.
- A new `INFORMATIONAL` set -- `forwarded_kwargs`, `id_match_consistency`, `deprecated_alias`, `code_only_ligand` -- is skipped by the global switch. Each reports a construction that works. Naming one in `BIOPIPELINES_ENFORCE_<CHECK>` still promotes it, since that is a deliberate choice about that check. The same command now fails one test, and that one is `unknown_kwargs` raising correctly on a real fault.

**A forced reinstall can no longer delete the framework's own environment**

- `_install_env` returns whatever the config maps a tool to, with no check that the env belongs to that tool, and `_env_remove_block` had no guard. `config.cluster.yaml` maps both `PLIP` and `Gnina` to `biopipelines`, so a forced reinstall of PLIP would emit `mamba env remove -n biopipelines -y` and delete the environment every other step activates. It is now refused, naming the entry and pointing at `environments/biopipelines.yaml`. Only the framework env is guarded; any other shared env still reinstalls.

**The run page carries structures, so it survives being copied off the cluster**

- A page opened on a laptop cannot follow a link into a compute node's filesystem, so a structure is inspectable only if its contents are inline. The structure renderer embedded the **first 50** whole files, which is both heavy and unrepresentative of a large campaign; it now embeds **five** -- the first three plus two sampled from the rest -- and the label says so. Below six, every structure is still embedded.
- The sample is seeded on the stream, not drawn fresh, because the page is regenerated after every completed step and a new sample each time would swap the structures under the reader.
- Both viewers embedded file contents into an inline script tag with `json.dumps`, which escapes quotes and backslashes but **not** the closing-tag sequence -- so a PDB REMARK carrying it closed the viewer's script early and whatever followed ran as markup when the page was opened. `pipeline_report` already neutralised the same sequence in the vendored library it inlines; the data beside it now gets the same treatment, and a test fails if any payload is added with a bare `json.dumps`. Stream ids are escaped before reaching `innerHTML`.
- `viewer_id` was `random.randint`, so two renders of an unchanged run differed on every element id. It is derived from the stream and its ids now. The existing regeneration test could not see this: its fixture config declares no renderers, so it never emitted a viewer.

**Three tool history entries were filed under the wrong tool**

- Every tool whose `history` was empty -- written on one line -- got its new entry appended *after* that line, which put it in the next tool's block. AlphaFold's landed in APBS, Mutagenesis's in MutationProfiler, Pool's in PoseBusters. The three donors were left with a bumped `current` and no history at all; two recipients held a duplicate version dated after their own `current`. Nothing could see it, because `check_tool_edits.py` only ever read `current`.
- The entries are back where they belong, and the gate now checks `history` structurally on every invocation: a duplicated version, a bumped `current` with an empty history, or a history head that is not `current`. It found a fourth problem immediately -- `StructureCluster` was the only tool with its history in ascending order.

**Tests that could not fail**

- `tests/tool_parameters` was **red for three days** and no CI job has ever run it: `f7fe128` moved LigandMPNN to an argv token array, replacing an `eval`, while the tests still asserted the old shell-string spelling. Both assertion helpers accept either spelling now, so the next wrapper to make that move needs no test changes. The marker's stated rationale -- "GPU-bound" -- is disproved by the suite running in **20 seconds with no GPU**; it remains excluded from CI, which is why it went red unnoticed.
- Sixteen of `tests/test_composer_agreement.py`'s thirty-six tests compared one implementation with itself: `_whole_set` and `_per_row` both called `predict_single_output_id`, differing only in how the test enumerated indices, and `_via_idset` called `compose_axes`, which `predict_single_output_id` also calls. Inverting the bundle-hoisting convention left all sixteen green. They now check against written-out expectation tables, and the same inversion fails **32 of 36**.

**Two relative imports that only fail on a compute node**

- Both paper pipelines were run at reduced scale to check this release. `compound_screening.py` failed at Boltz2, which generated **zero** configurations and then ran on zero inputs without raising anything of its own; the real error was three lines up in the log, an `ImportError: attempted relative import with no known parent package` from `combinatorics.predict_single_output_id`.
- A pipe script executes on a compute node where the package is not installed: it puts `biopipelines/` on `sys.path` and imports by bare name, so the module is top-level and `from .x import y` has no package to resolve against. Every other module in the tree guards this with a try/except that falls back to the bare name; two did not. `combinatorics.py`'s `from .idset import ...` dates to 2026-09-04 (`b1522f1`) and broke Boltz2 outright; `datastream.py`'s `from . import contract_enforcement` dates to 2026-09-02 (`4d7bfb6`) and broke the `ligand_utils` -> `biopipelines_io` -> `datastream` chain that the same two Boltz pipe scripts use.
- The suite could not see either, because a test imports `biopipelines` as a package, where the relative form works perfectly. This is the configuration-time / execution-time split again: what the tests import is not what the compute node imports.
- `tests/test_standalone_module_imports.py` closes the gap by reproducing the compute node rather than describing it -- a fresh interpreter with only `biopipelines/` on `sys.path`. It covers the transitive closure of the modules pipe scripts share, not a hand-kept list, and a separate test fails if a pipe script starts sharing a module the closure does not reach.

**A failing step was invisible three times over**

- Found by running `example_pipelines/CABSflex.py` at reduced scale. CABS-Flex aborted on the first structure (`Dynamic Kabsch did not converge in 100 steps`), never attempted the second, wrote **neither** a COMPLETED nor a FAILED marker, and `sacct` reported the job COMPLETED. Nothing anywhere said the step had failed.
- Three independent causes stacked. A step runs as `step.sh 2>&1 | tee log`, and a pipeline's exit status in bash is the last command's -- tee's, which is always 0 -- so the failure never reached the job. The tool exits from inside its own emitted bash on an upstream failure, which skips the block that writes its marker, so the step stayed unmarked; and unmarked reads as "not run yet" everywhere, including the run page, so a dead step is indistinguishable from a queued one. And the generated script sets neither `set -e` nor `pipefail`, so the run walked on into steps whose inputs were never produced.
- Fixed at the pipeline-script level, so no tool wrapper changes: each step invocation is followed by a guard reading `${PIPESTATUS[0]}` (the step's own status, not tee's) which writes the FAILED marker when the tool did not -- never overwriting a COMPLETED one the tool did write -- counts the failure, and lets the run continue as before. The job then exits non-zero at the end, after the page refresh, so a failed run still gets its page. Packed tasks exit their subshell instead, which is what the pack's existing `wait`-based counter was already looking for and never receiving.
- A second silence, found on the same sweep: AlphaFold ran to the end, found its outputs missing, wrote its own `003_AlphaFold_FAILED` marker and **exited 0**, so the `PIPESTATUS` guard could not see it and `sacct` again said COMPLETED. The end-of-batch check therefore counts FAILED markers as well as non-zero exits.
- The refresh moved from the last batch only to every batch. It had to: a batch that now exits non-zero cancels its `afterok` successors, so a run that dies in batch 1 would otherwise never reach the refresh and its page would stay the pre-run plan -- the exact failure this release already fixed once.
- **Behaviour change worth knowing about:** a run with any failed step now reports FAILED to the scheduler instead of COMPLETED, which means `--mail-type=FAIL` will start sending mail for runs that used to pass silently, and a failed batch cancels the batches that depend on it rather than letting them start on inputs that were never produced.
- `tests/test_step_failure_is_recorded.py` pins all of it, including that every step is guarded rather than just the last, and that the exit comes after the refresh.

**The run page on a cluster was never the run**

- `save()` writes `RunTime/pipeline.html` at configuration time, when nothing has executed, so a job appends a `python -c` that regenerates it at the end. That line has never once succeeded on the cluster. The job shell has only `module load miniforge3` applied, and its bare `python` resolves to a site interpreter with no pandas, so the import failed instantly -- and the line ended in `>/dev/null 2>&1 || true`, which discarded the traceback and the exit status together. Every cluster run page anyone has opened has been the pre-run plan: every node "pending", no completion status, and no 3D viewers, because the structure renderer reads the map_table and the per-id files, none of which exist yet at configuration time. Measured on a finished run: the page was 27 KB with zero occurrences of `3Dmol`; regenerating it by hand from the same graph gave 1.3 MB with sixteen, and the structures rendered.
- The refresh now activates the framework environment first, in a subshell so nothing it sources outlives it, using the same `activate_environment(name="biopipelines")` the completion check already uses. A failure prints a warning naming what the reader is looking at instead of vanishing; it still cannot fail the run, because the page is a convenience and not a result.
- `tests/test_page_refresh_environment.py` holds the emitted bash to activating before the interpreter under a real manager, to leaving the ambient interpreter alone under `pip`, and to never sending the refresh to `/dev/null` again. The silencing is what let this survive, so it is the part that is now asserted.

**A declined GPU was reported as one GPU**

- `Resources(gpu=None)` records `gpus: 1` alongside it, because the count defaults to 1 whether or not a GPU was ever asked for; the scheduler ignores the count and gates every directive on the spec. The run page printed the count. A CPU-only step therefore read `gpus=1, memory=4GB` on the very panel added so resources would be visible. SLURM was never wrong -- the emitted script carried no `--gres` and `AllocTRES` confirms `billing=1,cpu=1,mem=4G,node=1` -- so this was a reporting defect only.
- Two causes: merging batch resources onto a tool skipped `None` values, so a step that explicitly declined a GPU recorded no `gpu` key at all and the page could not tell refusal from absence; and `_fmt_resources` printed the count unconditionally. The key now survives the merge, and the report follows the scheduler's rule -- a count is shown only when a spec asks for GPUs, and a declined GPU reads `gpu=none`.
- Writing the agreement test surfaced a third, real defect: `gpu_spec == "none"` is case-sensitive and does not strip, so `gpu="None"` fell through to the generic branch and emitted `#SBATCH --gpus=None:1`, which SLURM can only reject. All four decline checks across the Slurm, LSF and PBS backends now compare stripped and lowercased.

**Pipeline: measured for a seam, found none, reduced instead**

- The earlier reviews called `Pipeline` the framework's real god object. It is, and the measurement says so in a way that also rules out the obvious fix. Splitting its 46 methods by what they do would move lines and change nothing: **every cluster shares 100% of its state with the rest** — script generation touches 19 attributes and all 19 are touched elsewhere, the run-record cluster 13 of 13, registration 13 of 13, debug capture 4 of 4. Four shorter files, one object exactly as coupled.
- The one cluster that looks like a concept, the batch plan (`batch_resources`, `current_batch`, `batch_parents`, `batch_start_indices`, `_packed_batches`), is not a seam either: **3 of 46 methods touch it exclusively**, totalling 47 lines, while ten reach across — `resources` alone touches six batch attributes and seven others.
- Nor is the file's apparent second half separable. `Parallel`, `Run`, `Service`, `Folder`, `Resources`, `Suffix`, `Save` and `Dependencies` are 597 lines that look independent and are not: every one mutates `Pipeline`'s privates from outside (`_parallel_anchor`, `_pack_runs`, `_packed_resources_seen`, `_folder_stack`, `_start_idx`, `_pending_after_parent`). Moving them would spread one object's invariants across two files. Of 37 instance attributes only four are touched by a single method; `folders` is touched by 19 methods and `tools` by 15.
- So the work done here is reduction, not decomposition, and the class is deliberately the same size — 1993 lines against 1990, because extraction moves lines rather than deleting them. What changed is that the three hardest methods are now readable and their tricky parts are named: `_generate_pipeline_script` 171 → 108 (the phase that settles every tool's inputs and outputs is now `_resolve_tool_outputs_and_write_configs`, which has to run first and in order because a tool's inputs resolve against the tools before it), `resources` 163 → 123 (`_batch_parent_edges` now names the two independent kinds of dependency edge and why a Service daemon must never be an afterok parent), and `__init__` 149 → 136 (`_default_local_output` states the three rules deciding where results land, and why Colab is the exception).
- Recorded so the label is settled by evidence rather than repeated: a decomposition of `Pipeline` would need its state split first, and nothing in the present shape offers a place to cut.

**The last two `eval`s in emitted bash are gone**

- HBDesigner and LigandMPNN both assembled their upstream command as a string and ran it through `eval`, which re-parses and strips one layer of quoting. The reachable vector was not the one expected: the *constraint values* are contained, because they sit inside double quotes after the re-parse and the four characters that matter there are exactly what the freeform denylist refuses. It was the **stream id** — `$STRUCT_ID` reaches `$OUT_DIR` and stream ids are validated nowhere, so an id of `x";>PWNED;"` executed a second command and silently truncated `--out_dir`. Measured, with the file it created.
- Both now build a bash array and expand it as `"${ARRAY[@]}"`, which passes each element as one argument with no second parse. That was already the house style in the three RFdiffusion wrappers; these two were the outliers. LigandMPNN's position resolver now prints NUL-separated argv tokens instead of a flag-plus-quoted-value line, which is precisely what its `eval` existed to split.
- Worth recording as the systemic finding rather than the local one: **a stream id gets no shell-safety validation anywhere.** That is harmless in a correctly quoted position, and it was the vector in both defects. The only `eval` left in the tree is `cli.py`'s conda shell hook, a quoted substitution of a known manager name.

**The forwarding gate is derived instead of curated**

- `FORWARDING_IMPOSSIBLE_TOOLS` named ten tools that supposedly could not forward. It was wrong about three — DynamicBind builds its own command line, GEMS and PLM_Sol reach `inference.py` through a subprocess rather than in-process — and, more to the point, it was **disjoint from the six tools that actually forwarded**, so `assert_can_forward` had never fired once, while roughly eighty genuinely non-forwarding wrappers were absent from it and would have accepted the marker and dropped its tokens.
- It is replaced by a question about the class rather than a list of names: does any wrapper in its ancestry call `extra_args_tokens()`, `extra_args_bash_tokens()` or `extra_args_bash()`? `extra_args_echo()` deliberately does not count — it announces the tokens in the log and places none of them on a command line, which is the exact silence the marker exists to remove.
- `tests/test_forwarded_kwargs.py` now **discovers** every tool carrying the marker instead of listing them, and requires each one's token to reach a real command line, with `echo` lines stripped so the announcement cannot answer for the command. A tool that gains the marker is tested by having gained it.

**Forwarding reaches thirteen more tools, by two routes**

- Added to AlphaFold, Boltz2, NeuralPLexer, Aggrescan3D, CABSflex, DynamicBind and LASErMPNN, whose own bash carries the upstream command, and to Gnina and Vina, whose argv is built in a pipe script. Those two needed the second route: the tokens travel in the config JSON as a list and the pipe script appends them to the command it hands to `subprocess.run`. That route is **safer** than the first — no shell is involved, so nothing re-parses and the metacharacter denylist is not load-bearing there. The discovery test accepts either, and for the config route checks both halves, because a JSON nobody reads back drops the tokens as silently as no JSON at all.
- **A dash-spelled upstream flag was unreachable.** The key allowlist took an identifier or a dotted path, so `--msa-mode`, `--weighted-fit` and `--num-steps` had no expressible form and forwarding was silently confined to parsers that happen to use underscores — NeuralPLexer's surface is almost entirely dashed, so its marker would have bought very little. An inner dash is now allowed; a leading one is still refused, so a forwarded key cannot impersonate one of the framework's own flags.
- `FORWARD_UNKNOWN_KWARGS` is documented in `docs/developer_manual.md`: the two dialects, the trade it makes (a configuration-time `unknown_kwargs` report becomes a runtime failure inside the tool, and only the typo check survives), the shell-safety rule and its `eval` reason, and the architectural fact that decides whether the marker can work at all.

**A bracket now honours the shape it names**

- `[...]` used to discard its content entirely, so `design_1[_<#>]` covered `design_1_ZZZ` as readily as `design_1_99` — it accepted a constraint and honoured none of it. A slot inside a bracket still cannot be *enumerated*, since the values arrive at runtime, but it can say what shape they will take: `<#>` is digits, `<?>` is any one segment, and a range or a list of several values constrains to exactly those. Measured against the real tool patterns: `Panda_1_[<#>]` now refuses `Panda_1_x`, `prot[_<#><A V L>]` refuses `prot_ZZ`, `c[<#>_<#>]` refuses `cA_B`.
- **A single bare word deliberately stays a wildcard.** That spelling predates the classes and was always read as a placeholder — `rcsb.py`'s whole-id `[<hits>]` means every row, and `[_<N>]` in an existing pipeline meant a number — so narrowing it silently would change which rows a pipeline selects.
- It costs nothing: a digit class branches less than an unconstrained segment, so rejecting a long non-matching id measures 0.30 µs against 1.21 µs for `<?>`. One care is needed and is taken — two adjacent *unconstrained* slots collapse into one, because `[^_]+[^_]+` inside a repetition backtracks exponentially over every split of the same run. Dropping that collapse regressed the linearity test, which is how it was caught.

**The run page's 3D viewers work offline**

- The py3Dmol library is vendored at `renderers/vendor/3Dmol-min.js` (3Dmol.js 2.5.2, BSD-3-Clause, hash-pinned by a test) and satisfied through a three-link chain: the vendored copy is inlined **once per page** however many structure nodes it has; failing that the CDN `<script>` survives under `allow_external=True`; failing that the node falls back to its metadata table, naming what was missing. A 5-step demo goes from 28 KB with no viewers to 695 KB with five, still one self-contained file. Verified independently: one embed, zero external `src`/`href`, 751 `ATOM` records.
- Committed rather than fetched on demand, because page generation runs on compute nodes and inside on-the-fly execution where there is often no outbound network — a fetch-on-generate design would degrade to the metadata table exactly where the page matters most.
- **`allow_external` no longer decides whether structures render**, which was the confusing part; with the vendored copy it is provably a no-op for the viewers. Its remaining job is renderer output that fetches *data*, so it stays off by default. Three places documented the old behaviour and were corrected: the user manual, the LLM contract, and `render_pipeline_page`'s docstring.
- Known and pre-existing, not a regression: neither the vendored asset nor `renderers/` reaches an installed wheel — `packages.find` includes only `biopipelines*`, and `renderers/` has no `__init__.py`. A non-editable install already cannot find `renderers/structures.py`, so it renders metadata-only nodes. Making the page work from a wheel means packaging `renderers` and listing the asset as package data, together.

**The environment standard, written down**

- **`env_manager: pip` was the one manager where the wrapper's literal beat the config.** `_install_env` returned `ENV_NAME` *before* consulting `environments:`, so a laptop config that did name an environment was ignored there. The config is now read first for every manager; pip is exempt from the *raise*, not from the config, because a laptop variant declares no `environments:` block at all.
- **pip mode stops pretending it can build an environment.** It emitted `pip env create -f ...` and `pip run -n ...`, neither of which is a pip command, so the script could only fail later and less legibly. It now refuses with a message naming the variant and what to do instead.
- **The standard: a spec file is named after the environment it defines.** An `environments:` entry names an environment; an environment is defined by `environments/<env>.<variant>.yaml`, falling back to `environments/<env>.yaml`. Nothing is keyed by tool name, which is why 23 tools share `biopipelines`, six share `ProteinEnv` and three share `SE3nv`, and why redirecting a tool is a one-line config change. Across `config.cluster.yaml`'s 77 entries there are 42 distinct environment names against 45 spec files, and 41 of the 42 have one.
- **A missing spec is not an error.** `RF3: modelforge` names an environment the upstream installer builds, so no spec exists for it on three variants. The emitted script now tries the variant spec, then the shared one, and otherwise says it is assuming the environment exists — rather than running `env create -f` on an absent file. An earlier attempt at this check in Python was wrong and is worth recording: the install script is generated locally and runs on the cluster, so the repo path it names is remote and a config-time `os.path.isfile` sees nothing, which would have skipped every create everywhere. `tests/test_cabsflex_colab.py` caught it.
- `tests/test_environment_resolution.py`'s redirect test asserted only that `env create` mentioned the new name; the fixture now writes a real spec for the redirected environment, so it proves the redirect end to end rather than half of it.

**The run page, after looking at it**

- The arrowheads were detached from their lines, rendering as `>-`. The cause was marker semantics: `refX`, the marker's own viewBox mapping and `markerUnits` interact, and the head landed beside the curve rather than on it. Markers are gone; the head is a plain triangle whose base sits exactly where the curve ends, and since the final segment is horizontal by construction it needs no rotation. Nothing now depends on how a browser resolves a marker.
- Every edge meeting a node terminated on the same point, because the anchor was `top + min(height/2, 17)` for all of them, so the heads piled up. Each end now takes its own slot on its own node and equal-span edges get spread bows. The SVG also stopped using a stretched `viewBox` with `preserveAspectRatio="none"`, which scaled x and y independently and skewed the heads further every time a card expanded and changed the height.
- **Order-only edges are no longer drawn.** Execution order is the order the steps are listed in, so a dashed arrow for it added nothing and invited being read as a dependency. The legend and the "show order-only edges" toggle went with them, and the "Recovered dataflow edges" table went too: the arrows now show every edge it listed, and the one thing a reader could not see for themselves — that an edge is drawn only where the consuming tool holds an object stamped with its producer — moved to the footer.
- The header gained the metadata worth having and lost the parts that were noise: steps in batches, dataflow edge count, biopipelines and Python versions, host. A tool's version now appears on **each use of that tool** rather than once as a roll-up, since two steps can run different versions. `scheduler` appeared in both the pipeline and machine panels and is now only in machine. Batch resources were shown in a summary panel as well as on every batch lane head; the duplicate panel is gone.
- Completed against failed is a donut in the top right rather than a "5 of 5" line, built from stroke dash offsets rather than arc maths.
- New **Machine** panel: scheduler, env manager, and on a cluster the modules, partition, account and container runtime. It is recorded into `pipeline_graph.json` at save time rather than read from the config at render time, because a page regenerated in a bare process auto-detects whatever variant that process resolves, which need not be the one the run used.

**One vocabulary for ids, and `<N>` stops meaning a number by accident**

- Renaming the id_map match classes to `<#>` and `<?>` left the callers alone, so the tools went on writing `<N>` where they meant a number. `mutagenesis.py:343` is the clearest case: it emits `[_<N><A C D...>]` whose runtime values are `prot_5A`, `prot_12V` — a position number followed by a residue letter — which is exactly the ambiguity the punctuation was introduced to remove.
- `id_patterns` now knows the same two classes. A class matches without enumerating, so it is only meaningful where matching happens: **inside a bracket**. Outside one it raises, naming what to write instead, rather than quietly becoming the one-element set containing `#`.
- Nineteen in-bracket occurrences across nine files were respelled `<N>` → `<#>`. That is behaviour-preserving — a bracket discards its content, since a value unknown at configuration time cannot be narrowed there — so the compiled regex is identical; the token simply stops lying. The enumerated readings are untouched: `<0..2>` and `<A V>` still hold literal values, and `<N>` outside a bracket is still the letter N. An enumerated `<S E>`, meaning serine or glutamate, is a value set and was left alone; no bare `<S>` existed in tool code at all.
- Not done, and worth deciding separately: a bracket still does not **enforce** its class. `[_<#><A V L>]` could match `_5A` and refuse `_XYZ`, which would have caught the ReMap defect below at configuration time, but it changes matching for every bracket site and belongs in its own change.

**Contract enforcement is for tool authors, so one switch turns it all on**

- These checks address whoever is writing a wrapper, not the scientist running a pipeline, so warning is the right default and a contract slip should not stop a run. `BIOPIPELINES_ENFORCE=1` now promotes every check to raise for a debugging session, and `true`, `yes`, `on`, `all` and `strict` work too, in any case.
- Previously only the three exact lowercase names were accepted and everything else fell through in silence, so `BIOPIPELINES_ENFORCE=True` left enforcement off while the caller believed it was on. An unrecognized value now says so once. This reverses an earlier deliberate choice that three tests pinned; those tests were rewritten to state the new contract rather than being quietly deleted.

**A bundle deduplicated across axes instead of within each one**

- Two bundled axes may legitimately carry the same id, and each still has to contribute it, or the id stops being reconstructible from the per-axis provenance columns. `predict_output_ids_with_provenance` deduplicates per axis and got this right; the runtime composer deduplicated across all bundle axes at once, and had done so before this wave as well. So with axes `{X,Y}` and `{Y,Z}` plus one iterated axis, the prediction was `X+Y+Y+Z+s1` and the production `X+Y+Z+s1` — a mismatch, and a `FAILED` marker. Fixed in `bundle()`; the 5634-case sweep that moved the composer is unchanged by it, because that sweep used distinct ids per axis and never reached this case.
- The gap survived the wave that was meant to close it because the agreement test compared two per-row loops rather than the two predictors. It now calls `predict_output_ids_with_provenance` for real, over both distinct and shared id sets, and the shared-id case fails against the old deduplication while every distinct-id case passes.
- A misspelled axis mode now raises instead of falling through to the iterated branch and quietly selecting one id. It used to raise too, but only by accident — the mode matched nothing, no parts were collected, and the "requires at least one axis" guard fired.
- The retired `<N>`/`<S>` id_map spellings now actually report themselves: `check_retired_class_spelling` was written but never called, so the promised `deprecated_alias` warning could not fire. It runs where every pattern is parsed. Three more sites still carrying the old spelling were migrated (`id_map_utils`' own internal fallback, `pipe_panda.py`, and `pipe_check_completion.py`).

**Angle brackets meant two opposite things, and one of them read as a residue**

- `id_patterns` uses `<...>` to compact an id that is already **predictable**, so a slot holds literal values: `<0..2>` is three ids and `<N>` is the single id `N`. `id_map_utils`, written a week earlier for the unrelated job of walking up a parent chain, used the same brackets for **match classes**, where `<N>` meant any run of digits. The same token was a literal in one module and a wildcard in the other, and the tool code has been writing `[_<N>]` meaning a number while `expand_pattern` read it as the letter.
- A lettered class cannot survive in this domain, which is what settles it rather than taste: `<N><S E>` reads as serine or glutamate at position N, while `<15 16><N>` reads as asparagine at positions 15 and 16. The classes are punctuation now — `<#>` for digits, `<?>` for one segment. The letter spellings still work, because an id_map can arrive from a user's JSON, and report themselves through the existing `deprecated_alias` check.
- `[...]` constrains nothing, and that is the design rather than an oversight: it marks a value not knowable until the upstream tool has run, so there is nothing there to narrow. Its content is discarded — `prot[_<N>]`, `prot[_<S>]` and `prot[_<A V>]` all compile identically, and `design_1[_<N>]` selects `design_1_ZZZ` as readily as `design_1_99`. That is now stated in the manual and pinned by a test, because the notation had been inviting the opposite reading.
- The delimiter and the "one segment" rule now have one definition, `id_patterns.SUFFIX_DELIMITER` and `SEGMENT_REGEX`, which `id_map_utils` imports. They had been spelled independently in both, so changing what separates a parent from a child would have moved one and not the other. That was the entire legitimate overlap between the two modules — the rest genuinely differs, since `id_patterns` generates ids from a pattern while `id_map_utils` reduces one id to its ancestors, and its `*` backreference has no counterpart at all.

**One composer for the runtime path**

- `predict_single_output_id` is now implemented on `IdSet.compose_axes` rather than being a second implementation that happened to agree with the whole-set predictor. Verified byte-identical over a 5634-case sweep of axis counts, modes, static sets and orderings before and after the move: zero differences. `compose_axes` gained the static dimension to make that possible, which is where `Bundle(Each(a), b)` belongs — the static companions decorate their own axis's contribution rather than becoming an axis.
- `predict_output_ids_with_provenance` was deliberately **not** collapsed. Its provenance is computed inside the product loop, interleaved with the ids, and rewriting it would change the prediction path of the nine tools that call it, for de-duplication alone. `tests/test_composer_agreement.py` now compares it against the runtime composer directly — an earlier version of that test compared two per-row loops with each other and never called the whole-set predictor at all, so an earlier draft of this entry claimed a guarantee the test did not provide.

**`IdSet`: ids get a type, and the axis convention gets a name**

- An id was a `str` and an id set a `List[str]`, so every rule governing them lived as a free function in `id_patterns` to be remembered at each call site. `biopipelines/idset.py` gives them one home. It is a pure value type — ids and nothing else, no map_table and no file handles — comparable, hashable and testable on its own, with exactly the four operations by which ids are ever combined: bundling, cartesian product, suffix multiplication and renaming. A rename is cardinality-preserving and one that would collapse two ids raises, because provenance columns join on the id.
- `len(ids)` counts declared ids and `ids.count()` counts what they expand to, and they differ on purpose: at configuration time an expansion is often not knowable, and a count you cannot compute is worse than the one you can. `ids.enumerated()` returns all the concrete ids when the set is expandable and ids still carrying their unexpandable parts when it is not.
- `compose_axes([(ids, mode), ...])` names a convention that had been an emergent property of a 150-line function: **a bundle prefix comes first, ahead of the iterated axes and regardless of declared order.** It agrees with the shipped composer on every axis-mode combination. The convention deliberately does not live in `product`, which stays the honest order-respecting cartesian product — by the time a product runs, `bundled()` has collapsed the axis to an ordinary one-element set and there is nothing left to say which operand was a bundle.
- The consequence is worth stating because getting it wrong is silent: **an id cannot be decomposed by splitting on `+` and pairing positions with declared axes**, since a bundle occupies as many positions as it has members and not the position it was declared in. Record what each axis contributed while composing instead.
- `tests/test_composer_agreement.py` makes `predict_single_output_id`'s docstring claim — that per-row and whole-set generation "always agree" — an actual swept property over every axis-mode combination for two and three axes, and asserts `IdSet` composes the same ids. It was aspirational before; nothing checked it.

**Mock's provenance was assigned by position, and every column could be wrong**

- `pipe_mock.py`'s `_rebuild_runtime_provenance` recovered per-axis provenance by splitting the parent id on `+` and giving part *i* to axis *i*. Both halves of that are unsound: a bundled axis contributes several `+`-joined parts for one axis, and the composer hoists it ahead of the iterated axes. Measured with `Bundle(compounds)` and `Each(structures)`: `structures` was assigned `LIG1`, a ligand id, and the remaining columns shifted behind it. Silent, and the provenance column is what downstream joins on.
- Provenance is now recorded during composition, where each axis's contribution is still known, and the runtime result matches the config-time declaration exactly — including the per-member `<axis>.<n>` bundle columns. The positional path stays only as the fallback for a config written before axis metadata existed.

**Six tools were checked for the same handoff, and none of them had it**

- `diffdock`, `dynamicbind`, `neuralplexer`, `placer`, `pocketgen` and `rtmscore` all compose ids by hand at runtime with a flat `<a>+<b>` join that cannot express a bundled axis — the exact shape of the Mock defect. None of them can reach it: every one of the six refuses a `Bundle`/`Each` wrapper at construction, accepting only a `DataStream` or `StandardizedOutput`, so both axes are always iterated and a flat product is the framework's product. Established by removing each guard experimentally and reproducing the Mock signature (the three bundle combinations diverge, the pure-`Each` pair does not), then restoring it. The refusal is load-bearing rather than incidental, and each tool now has a test file pinning both halves, so widening a guard fails loudly and forces the runtime onto the shared composer at the same time.
- Worth recording about `rtmscore` specifically: nothing predicts its output ids at all. It declares tables and no streams, so `pipe_check_completion` derives an empty declared-id list from it and its `<protein>+<ligand>` join key reaches no completion check. Anyone adding a predictor must reproduce a data-dependent branch rather than assume a product — when both input streams carry identical id lists the tool takes the diagonal, and 376 by 376 would be 141 376 runs of which 375 in 376 score against the wrong protein.

**Selecting one id no longer hands back another id's file**

- `StandardizedOutput.__getitem__` resolved a file by position: `idx = ds.ids_expanded.index(key)` indexing into `ds.files`. When a stream declares explicit files against unexpanded pattern ids those lists are in different index spaces, and the mismatch was silent both ways. Measured on a two-pattern, six-id stream: four ids came back with no file, one came back with the *other* pattern's file, and one came back holding a pattern where a path belongs. The wrong-file case is the dangerous one, because nothing downstream can tell it from a correct answer.
- An id whose file cannot be resolved now raises and names both index spaces (how many explicit files against how many expanded ids, and how many before expansion), so the caller knows which list to fix. The shapes that do resolve are unchanged: a `<id>` template, a shared file, or one explicit file per expanded id.
- `tests/test_output_id_selection.py` pins it, including a guard that no id can ever receive a path not containing its own id. Eight of its eleven cases fail against the positional behavior.

**The bracket contract, written down and made linear**

- `parent_[<N>]` compiled to `(?:[^_]+)*`, which matches the same ids as `[^_]*` but treats every split of a delimiter-free run as a candidate: rejecting a non-matching id cost 2**n, measured at 0.36 s for 24 characters and double for each one after. That spelling appears 6 times in `biopipelines/` and `[_<N>]` 13 times, so a long id on either would have hung a run rather than failed it. Emitting `[^_]*` for the single-slot case fixes it in place — selections are byte-identical, and Python 3.10 has no atomic group to express the intent directly.
- The two spellings are now in `developer_manual.md`, which documented only `design_1[_<N>]`. Where the delimiter sits is the whole difference and neither is a special case: **inside** the bracket each repetition carries its own, so the suffix is optional and repeatable (`parent`, `parent_4E`, `parent_4E_6U`); **outside** it, the value cannot cross a delimiter, so the group collapses to at most one suffix, and since the bare `parent_` is never a real id this selects exactly the ids that are `parent_` plus one value — what a flat renumber wants.
- Both are pinned by `tests/test_id_pattern_selection.py`, including a linearity test deliberately sized at 26 characters: longer and the unfixed regex never returns, so the test would hang instead of failing.

**The framework stops guessing** — undocumented until now, and the most user-visible change in the release

- **An unresolvable config refuses instead of picking one.** `ConfigManager` used to fall back to a variant when no `config.<variant>.yaml` claimed the current user, so a developer on an unclaimed machine silently ran against someone else's scheduler, folders and environments. It now raises, naming what it looked for, which variants it found, and that none of them claims this username (`config_manager.py:196`). `config.colab.yaml` is deliberately excluded from the scan; it is selected inside Colab instead.
- **`Load` recovers what a step did produce.** A declared-but-absent `tables/missing.csv` is what a job killed mid-write leaves behind, and raising on it denied the user every id the step *had* finished; it now warns, excuses no ids, and carries on (`load.py:871`).
- **`Load` stopped mismatching ids to files.** Substring matching in declared order paired `design_10` with `design_1.pdb` and reported `design_1` twice. Exact basenames now claim first and one file serves one id (`load.py:643`).
- `table_utils` no longer relies on `TableInfo.__getattr__` answering any name; the permissive behavior itself was pinned as a strict xfail and resolved later in the release.
- Not recorded at the time, and worth knowing when reading the older bullets: the framework version stayed `1.4.0` through all of this, and the `unknown_kwargs` bullet further down describes the forwarding design that came after, not the first cut that only reported.

**The on-the-fly run page had a frame and no content**

- `_export_tool_outputs()` was called only from `save()`, and the on-the-fly path never calls `save()` — that being the premise of refreshing the page after each step. So `ToolOutputs/` was never created in the mode the refresh was built for, and every step card rendered the `no exported output inventory` placeholder. The degradation is itself deliberate and tested, which is why nobody noticed one mode always took it. The on-the-fly step now exports the inventory before refreshing the page: a local two-step `Mock` run goes from 16 129 bytes with one placeholder to 18 246 bytes with none, and writes the two `ToolOutputs/*.json` it never wrote before.
- Pinned by a call-order test rather than a page-content test. A content test cannot tell the two paths apart on the local fixture, because `on_the_fly=False` makes `__exit__` call `save()` and export anyway — the first attempt at such a test passed before the fix as well as after it, and was deleted rather than kept as decoration.

**A forwarded value can no longer smuggle shell syntax through `eval`**

- Forwarded kwargs were validated with the same denylist as every other user string, which refuses only the four characters that break double-quoted interpolation. That is the right denylist for a value emitted into a double-quoted position, and five of the six emission sites are exactly that. LigandMPNN's is not: it emits through `eval` (`ligand_mpnn.py:379`), which re-parses the line and strips one layer of quoting, so a `;` in a forwarded value started a new command on the compute node. Confirmed by generating the step script and running the emitted line under bash.
- Forwarded values now additionally refuse `;`, `|`, `&`, `<`, `>`, `(`, `)`, carriage return and newline. These are never part of an upstream command-line value, so the guard costs nothing: `chain A`, `A10-A20`, `a,b,c`, `key=value` and paths all still pass, and both sets are pinned by `tests/test_forwarded_kwargs.py`.
- The guard sits on the forwarded path only, not on `_validate_freeform_string`, because a typed parameter emitted into a quoted position has legitimate uses for these characters and is not re-parsed.

**`base_config.py` becomes three layers**

- `base_config.py` held nine classes, seven of which now live elsewhere — a god *file*, not a god object. It is now `table_containers.py` (`TableMetadata`, `TableInfo`, `IndexedTableContainer`, `TableContainer`, `StreamContainer`, `resolve_table_reference`), `outputs.py` (`StandardizedOutput`, `ToolOutput`), and `base_config.py` (`BaseConfig`, `_Installer`, the alias machinery, extra-args rendering and the dataflow-edge helpers), layered in that order. Only the five-class table cluster was genuinely independent of `BaseConfig`; `StandardizedOutput` and `ToolOutput` do relate to it, which is exactly why the annotation coupling existed. 3194 lines became 1900 + 1009 + 374, i.e. 3283 — the extra 89 are the two new modules' headers, docstrings and import blocks.
- Every moved name is re-exported from `base_config.py` as the identical object, so the ~90 modules importing them are untouched and both spellings of the dual-import idiom keep working. The only coupling that pointed the wrong way was `ToolOutput.__init__`'s `config: BaseConfig` annotation; quoting it removed the cycle, and `TYPE_CHECKING` keeps the type visible to tooling.
- `tests/test_module_layering.py` pins the layering: the lower layers must not import the higher ones (a *deferred* back-import counts), each re-export must be the identical object, and `biopipelines.__all__` must not promise a name the package lacks. Its first cut let two mutations through — it inspected only `ast.ImportFrom`, so a bare `import biopipelines.base_config` inside a method passed, and it compared only an import path's first dotted segment, so `from biopipelines.outputs import ...` inside `table_containers` read as importing `biopipelines`. It now walks both statement forms and every segment. Five mutations are on record as caught: a rebound re-export, a top-level back-import, a function-local `from`-import, a function-local bare `import`, and a fully-qualified cross-layer import.
- `biopipelines.__all__` promised four names the package did not expose, and the fix differs per name. `DataStreamResolver`, `resolve_to_datastream` and `resolve_input_to_datastream` all exist in `datastream_resolver.py` and six tool modules use the last of them — they were simply never imported into `__init__.py`, so they are now imported and the promise is kept. Only `PoseBustersTool` does not exist anywhere; that one is removed.
- Not done, and deliberately: `TableReference` stays in `biopipelines_io.py`. It was thought to live there to dodge an import cycle with `TableInfo`, but `biopipelines_io.py` never referenced `TableInfo` outside a docstring — there was no cycle, and moving it would only push `TableReference.resolve()`'s use of `load_table` into a function-local import. The new module is named `table_containers.py`, not `tables.py`, because `table.py` (the Table tool) and `table_utils.py` already exist.

**The pipeline draws itself**

- A `StandardizedOutput` now carries a back-reference to the tool that produced it, so the dataflow graph is recoverable. It was not: `ToolOutput` kept `.config` but `StandardizedOutput` kept only a dict, and `BaseConfig.__new__` returns the latter for chaining — so the object users pass between tools was precisely the one that had forgotten where it came from. `Pipeline` walks each new tool's arguments centrally and records the edges, rather than asking 92 tool authors to fill in the `input_sources` field that has sat there being populated by two of them.
- Recovered: whole outputs, bare `DataStream`s left behind by input normalization, `Bundle`/`Each` and lists of them, and outputs derived by indexing, iteration or `chunks()`. Not recovered, and pinned by a test so it stays honest rather than guessed: streams derived *inside* `DataStream` (`stream.chunks`, `stream.slice`), which builds fresh objects without copying the producer, and `TableInfo` inputs, which carry no back-reference at all.
- `save()` writes `RunTime/pipeline.html` beside `pipeline.sh`, and `RunTime/pipeline_graph.json` alongside it. The page lays the run out as one lane per batch with its resources and dependencies, each step a collapsed card carrying paths, version, resources, environment and completion marker, and an SVG gutter drawing solid arrows for recovered dataflow against dashed for order-only — so a sequence is never mistaken for a dependency. It is useful before a run too, when it shows structure and wiring and says outputs are pending.
- The page is self-contained: no CDN, no network, openable from a file:// URL after being copied off a cluster. It reuses `renderers/` through the same dispatch the framework already uses rather than reimplementing rendering, and a renderer that needs the network — `structures.py` and `grids.py` both pull py3Dmol — is dropped and named rather than silently producing a page that only works online. `regenerate_pipeline_page` rebuilds it from the graph after a run.

**ID matching says how sure it is**

- The match ladder knew which tier answered and threw it away. It now returns the tier, and a lookup is scored by the *consistency* of its tiers rather than their depth: a tool renaming every id degrades every row identically and scores 1.0, because that is the case the permissiveness exists to serve, while three rows of five hundred degrading differently scores 0.01 and names them. Fewer rows affected scores worse, deliberately — a rare minority is evidence of an accident rather than a rule.
- Log-only, through `contract_enforcement`, and silent unless a lookup is actually mixed. Measured across the whole suite: 90 in-process lookups, every one scoring 1.0, so this is quiet in practice. The ladder turns out to have five answering tiers grouped into four documented priority levels, which is why two earlier audits disagreed about the count and both were right.

**Contract enforcement**

- Unknown constructor keywords are no longer silently parked. `BaseConfig` stored anything it did not recognise in `self.params` and never read it again, so a misspelling and a deliberate upstream flag were equally invisible. `check_kwargs` now splits the leftovers: a key close to a typed parameter name is reported as a probable misspelling naming the candidate, and a key on a tool that declares `FORWARD_UNKNOWN_KWARGS` is announced and rendered onto the upstream command line. `FORWARDING_IMPOSSIBLE_TOOLS` makes the marker an import-time error on a tool that runs its model in-process and has no argv to append to.

- New `biopipelines/contract_enforcement.py` is the single home for the framework's contract checks. The contracts are stated in the developer manual but were previously prose only, so they were violated silently — and in the case of the Ligand Contract, taught wrongly by the manual's own tool template, which five tools then copied. Each check is a pure function returning a `Violation` or `None`; callers pass the result to `report()`, which acts on the check's severity.
- Severity is per-check with a global default, resolved most-specific-first: `BIOPIPELINES_ENFORCE_<CHECK>`, then `BIOPIPELINES_ENFORCE`, then the module's `SEVERITY` table, then `DEFAULT_SEVERITY`. The global switch deliberately outranks the table, because every check lives in the table and consulting it first would leave `BIOPIPELINES_ENFORCE` unable to affect anything. Everything ships at `warn`, so a violation is reported on stderr without failing a pipeline that would otherwise run; a check is promoted to `raise` once the warn phase shows the tree is clean. Warnings are deduplicated, so a violation inside a per-id loop prints once rather than hundreds of times.
- Two contracts are executable now, checked from `DataStream.__post_init__` above its early returns so pattern and shared-file streams are covered too: a `compounds` stream must declare `format="csv"` and never coordinates (`developer_manual.md:183`), and a value-based stream (`files=[]`) must declare `csv` (`:167`). Both exempt an empty `DataStream.empty()` placeholder, which means "this tool emits none of these" rather than "value-based" — without that exemption the check fired on nine first-party tools that are behaving correctly.
- A third check reports a stream name the framework does not know. It needed two things before it could be useful, and both arrived: warnings now name the tool that built the stream, via a context a generated wrapper around each subclass's `get_output_files()` enters, and a tool whose stream names come from its *user* rather than its wrapper — `Mock(streams={...})` and `Scripting` — sets `USER_STREAM_NAMES = True`, which drops the name check for that tool alone while the format checks still apply. It ships at `warn`, and both suites report no violations.

**One column-reference normalizer**

- `base_config.resolve_table_reference(value, parameter)` is now the single place a documented column reference becomes a `TableReference`. The conversion was copied into `pdb.py`, `rdkit_descriptors.py`, `hbdesigner.py` and `lasermpnn.py`, and simply missing from ProteinMPNN and LigandMPNN, which is why the documented tuple crashed on exactly those two. It accepts a literal string, a `TableReference`, a `(TableInfo, column)` tuple or a `(path, column)` pair, passes `None` through, and otherwise raises naming the parameter. The four pre-existing copies still have their own private helpers and should be folded into this one.

**Parameter aliases**

- `BaseConfig` gains `PARAMETER_ALIASES` (`{alternative spelling: current parameter name}`) and `DEPRECATED_ALIASES` (which of those keys are retired rather than first-class). Every tool constructor ends in `**kwargs`, so renaming a parameter used to mean a pipeline written against the old spelling kept running with the value never bound and the parameter at its default. Aliases are resolved by a wrapper `__init_subclass__` puts around the tool's `__init__`, so they land before the constructor binds anything: an aliased key is never a leftover kwarg, and is therefore neither reported as a probable misspelling nor rendered onto a forwarding tool's upstream command line. `RFdiffusion3(contigs=...)` did both.
- Two guards fire at class creation rather than at call time, since an alias that binds nothing is the silence the mechanism exists to remove: an alias whose target no constructor parameter names, and a `DEPRECATED_ALIASES` entry absent from `PARAMETER_ALIASES`. Both raise `ValueError`. A key the framework itself reads (`name`, the job name) is copied rather than moved, so the tool and `BaseConfig` both see it — that is what lets `Table` keep `name` as a synonym while the job name reaches the framework again. For any other key, passing both spellings raises.
- Two checks join `SEVERITY`, both at `warn` and gated like every other contract: `deprecated_alias`, reported when a retired spelling binds (the value still binds, so the pipeline runs), and `code_only_ligand`, reported when a `Ligand` is built from `codes=` alone and so carries a residue code but no chemistry. The second exists because unifying `code`/`codes` means a forgotten `smiles=` now produces a stub instead of raising; it is suppressed for the documented `ligand="LIG"` shorthand, where naming a residue is the whole intent.

**The lazy-id bracket contract**

- `[...]` is now matched as what it means: an **optional, repeatable** suffix group whose slot values never cross the `_` suffix delimiter. Two rules, and where the delimiter sits does the rest, with no special cases. `parent[_<N>]` puts the delimiter inside the group, so each repetition carries its own and the group is genuinely optional and repeatable — it covers `parent`, `parent_4E` and `parent_4E_6U`. `parent_[<N>]` puts it outside, so a value cannot cross a delimiter and the group collapses to at most one suffix, which is what a flat renumber (`name_1`, `name_2`) wants. Both existing spellings in the tree were already correct and no producer changed; `id_map_utils` was already deriving the delimiter the same way.
- The practical defect this fixes: `select_ids` matched by unanchored glob, so a pattern for designs 1-2 also selected 10, 11 and 12, and with zero-padded rows it returned *only* the wrong ones. Any pipeline with ten or more designs that narrowed a lazy stream computed every downstream count and statistic on the wrong set.
- `pipe_check_completion` no longer trusts a glob to decide what a lazy pattern covers. A glob cannot express an optional repeatable group, so it is used only to enumerate candidates on disk and `select_ids` decides which count. Previously a lazy stream could be reported COMPLETE off a *sibling* id's files. `glob_from_lazy` stays deliberately loose and its docstring now says so.
- Bounding each repetition by the delimiter also removed a pathological case: a pattern with several brackets against a long non-matching id used to backtrack for minutes and now resolves in well under a millisecond. Compiled patterns are cached, and the completion check calls the matcher once per stream rather than once per file.

**Python version support**

- `requires-python` widens to `>=3.10`, and `pyproject.toml` is now the authoritative declaration — `environments/biopipelines.yaml` carries a comment saying so. The former `<3.13` cap was copied from the conda spec when the project was made pip-installable and reflected RDKit and Biopython lacking cp313 wheels at the time; both ship them now, and the full suite passes on 3.13. The cap meant anyone on current Python hit `requires a different Python` at install time.
- CI adds Python 3.13 to both matrices, so the supported range is tested rather than asserted. The previous matrix tested exactly the pinned range, which is why the stale cap could not surface.

**PDB fixed-column parsing with 5-character CCD codes**

- `pdb_parser`'s field accessors parse by *shifted column* rather than by tokenizing. The residue-name field is 3 wide but the PDB now issues 5-character codes (`A1EI4`), and such a record pushes every later field right by its excess width — 2 columns, measured against RCSB's own output for 9RTM. The previous fix fell back to `line.split()` past column 17, which works only when every field is present and separated: a **blank chain id** (routine in this repo's own tool-generated ligand PDBs) shifted the token list by one so `field_res_seq` returned the x coordinate; an **insertion code** glued onto the residue number; and two **adjacent full-width coordinates** (`-100.123-100.123`) were one token. In every case `int()`/`float()` raised and the atom was silently dropped, so an entire ligand could vanish from a parse while the distances, autobox centres and atom counts computed from what survived all looked plausible. `_residue_shift` now derives the offset from the code's width and one code path serves both layouts.
- Both PDB parser loops report the records they skip instead of dropping them mutely. The silent `except … continue` is what kept the above invisible; a dropped record now names its exception and the offending line on stderr.
**Container ⇆ environment execution switching**

- New `biopipelines_io.container_argv_prefix(prefix)` splits a tool's `container_prefix()` string into argv tokens for a helper to prepend to a binary subprocess, so the external binary runs inside the configured `.sif` while the helper's own (biopipelines-importing) Python keeps running in the activated host env.
- New `BaseConfig.warn_container_unsupported()` emits a runtime warning when a container is configured for a tool that runs its model in-process or dispatches host-env sub-processes and therefore cannot use it; such a tool falls back to environment mode instead of silently ignoring the setting.
- New `BaseConfig._container_pull_block(folders, force_reinstall)` emits install-time bash that pulls a tool's container image when both a destination `.sif` path (config `containers:`) and a source URI (new `environments/_containers.yaml`, keyed by `TOOL_NAME`) are present; skips when the file exists (unless `force_reinstall`) and no-ops in env mode. Source (repo-versioned) and destination (deployment config) live apart by design.
- The developer manual gains a "Containerization" section: the `container_prefix()` seam and the two tool architectures (heavy command emitted directly in bash vs. binary invoked inside a host helper), that environment activation still happens in container mode (the prefix wraps only the binary), the ESMFold-style split / warn fallback for in-process tools, and the per-iteration container-startup caveat with the persistent-instance (`apptainer instance start/exec/stop`) escape hatch.

## [1.3.0] — 2026-06-26

A feature release on top of `1.2.0`: support for LSF and PBS/Torque batch schedulers alongside SLURM, a reworked stitch/combinatorics provenance scheme, and assorted stream-resolution and tool fixes. Contains one backward-incompatible API change (see below).

### Framework

**Batch schedulers (LSF, PBS/Torque)**

- The submission path is no longer SLURM-only. A new `biopipelines/schedulers.py` introduces a `SchedulerBackend` abstraction with `slurm`, `lsf`, and `pbs` backends; `Pipeline` generates native `#SBATCH` / `#BSUB` / `#PBS` directives for the configured scheduler, and the `submit` wrapper drives `sbatch` / `bsub` / `qsub`, capturing job ids to chain dependent batches. The same `Resources(...)` call is portable across all three.
- `machine.scheduler.name` now accepts `lsf` and `pbs` in addition to `slurm`, `colab`, and `none`; `bp-config auto` detects the scheduler from `sinfo` / `bsub` / `qsub` on PATH. GPU and memory specs are translated best-effort per scheduler (LSF memory to MB plus a matching `rusage`, walltime to `[HH:]MM`; PBS as separate `-l` requests); a constraint-style GPU spec with no native equivalent falls back to a plain GPU-count request with a printed warning. Scheduler-native knobs pass through `Resources(**options)` under the active scheduler's options key (`slurm_options` / `lsf_options` / `pbs_options`). Generated scripts are stemmed by scheduler (`slurm_batch*.sh`, `lsf_batch*.sh`, `pbs_batch*.sh`).
- The `submit` and `run` wrappers now export `BIOPIPELINES_CONFIG_VARIANT` and deep-merge the user overlay (`.config.<variant>.yaml`) when reading the scheduler block, so the bash and Python sides always agree on the active variant and on the resolved scheduler/modules/init.
- **Breaking:** `Pipeline.slurm()` is renamed to `Pipeline.generate_job_scripts()`, the `slurm_script` attribute to `job_script`, and `ConfigManager.get_slurm_modules()` to `get_scheduler_modules()`. The old names are removed (no aliases). Pipeline scripts that called `p.slurm()` directly must switch to `p.generate_job_scripts()`; the common `with Pipeline(...)` auto-submit path is unaffected.

**Combinatorics and stitching**

- `assemble_provenance_id()` is the single source of truth for `+`/`_` id assembly. StitchSequences over tool axes now emits `+`-joined provenance ids (e.g. `pdb_3_5+pdb_3_2`) plus `sequences_k.id` columns rather than positional `_`-joined ids, while raw/marker axes keep `_<i>` fallbacks; the config-time predictor mirrors the runtime exactly. Combinatorics accepts a bare filtered `DataStream` as an axis source.

**Stream resolution and id filtering**

- Id filtering supports pattern selection over `map_table` rows with bracket-preserving expansion. `map_table` is treated strictly as a runtime artifact: config-time `create_map_table` is dropped from `get_output_files` (with a documented exception for `Load`).

### Tools

- **DNAEncoder** — its stream is the content table (`sequences/sequences.csv`) and emits a canonical `sequence` column.
- **ProteinMPNN** — adds SolubleMPNN alias for soluble_model=True; switched parameter default back to False.

## [1.2.0] — 2026-06-11

A large release on top of `1.1.1`: a config-system overhaul, a reworked output/datastream contract, ~30 new tool wrappers, full Google Colab support alongside the cluster path, and a self-hosted MMseqs2 CPU search server.

### Framework

**Configuration system**

- New variant-aware config layout: `config.<variant>.yaml` ships committed defaults; user edits land in a gitignored `.config.<variant>.yaml` that is deep-merged on top at load time, so pulling repo-config changes never clobbers local settings. `machine.env_manager` and `machine.scheduler` are now dicts; folder layout moved from CamelCase to snake_case; config and execution output folders are separated.
- New `bp-config` CLI: `path` (prints the active config path — pipe it into an editor with `$EDITOR "$(bp-config path)"`, `--base` for the committed file), `edit`, `list`, `show` (faithful YAML dump with an arrow-key variant picker), `set`, and `auto`. `set`/`auto`/`edit` write only the overlay (`set` validates against the base, `edit` shows the merged tree and saves the diff, `auto` host-probes the machine block and diffs against base+overlay). `get`/`set` work non-interactively for scripting.
- `bp-config edit` opens an interactive arrow-key TUI (`biopipelines/config_editor.py`, prompt_toolkit-based): expand/collapse, in-line value editing with type-preserving coercion, search, and atomic save. Round-trip uses `ruamel.yaml` so comments and key ordering survive. Every config write takes a timestamped `<name>.<YYYYMMDD-HHMMSS>.bak`, so successive edits never clobber the previous backup.
- `prompt_toolkit>=3` and `ruamel.yaml>=0.17` are now required dependencies (not optional extras), so `bp-config edit` is always available. `rdkit` is also promoted to a core dependency. `pyproject.toml` declares minimum version floors for the framework's Python deps.

**Output and datastream contract**

- Per-tool outputs are standardized as typed streams. `DataStream.files` widens to `Union[str, List[str]]`: a single non-empty string now denotes one shared artifact covering all ids (e.g. a multi-record FASTA), in addition to the empty-list (value-based) and per-id-list forms. Every consumer handles the shared-file form explicitly — no silent copy-whole-file fallback.
- New `biopipelines/stream_slicers.py`: a registry of format-keyed slicer and merger functions (ships FASTA and CSV). Unknown formats raise rather than copying a whole file, so a filter step can never leak stale records downstream. FASTA header tokenizer handles rich upstream headers (`>4LCD, score=...`) while preserving NCBI-style `sp|P12345|FOO` ids.
- Canonical per-tool output layout unified as `_configuration/`, `_execution/`, `<stream>/`, `tables/`, `_extras/`.
- Missing-manifest cascade owned by `BaseConfig`: multi-axis propagation and provenance-aware completion remap; `missing.csv` carries a `kind` column (`FAILED` only on local failures, not upstream-filtered ids). Excusal matches on each path's owner id (threaded through the `<id>` substitution), not the filename basename, so templates that place `<id>` off the stem are excused correctly, including lazy fan-outs the config-time remap can't pre-expand.
- `get_mapped_ids` provenance overhaul: O(N²) → O(N) id-matching; closest-siblings-only design-group matching (stops a cross-design Cartesian explosion in StitchSequences); table lookup unified on `get_mapped_ids`. `pipe_check_completion` runs under Python 3.8 tool envs (`typing.Tuple`).

**Pipeline orchestration**

- `Parallel()` context manager + DAG batch-dependency machinery for splitting a run across SLURM jobs.
- `Pool` tool: gather N parallel runs into one `StandardizedOutput` (`runs=` list, `streams=` subset, `recount_prefix` opt-in renumber).
- `LoadMultiple` nests its `Load` steps under `Folder("LoadMultiple")` by default (`folder=None` opts out); accepts any-length step prefix.

- Panda provenance: chained stream-map writes rename `<stream>.id` → `<stream>.-1.id` (negative integers reserved for chained-generation tracking, can't collide with Bundle's non-negative `<stream>.N.id`), so `Mock → Panda → Panda` chains stay resolvable. Implicit source tagging on concat; `zscore` op (population std, optional by-group + sign flip).

- mmCIF parsing in the shared structure reader (CIF-correct loop tokenization and null handling, prefer `auth_atom_id`); centralized fixed-column field accessors as the single source of truth for ATOM/HETATM layout, routed through every per-pipe-script reader.

**Shell-safety**

- Systematic shell-safety pass across all tools: free-form string params and shell-unsafe input validated in `Pipeline`, config, and the tool base; tightened machine-enum validation; description escaping counted as its own layer. Layers documented in the developer manual.
